# GeneratorAI workflow author

<!-- Generated by scripts/generate-workflow-skill.ts from @generatorai/workflow-spec. Do not edit. The hand-written parts live in scripts/workflow-skill/. -->

A GeneratorAI workflow is ONE JSON document, a `WorkflowGraph`: `{"formatVersion": 2, "workflow": {…}, "stages": […], "edges": […]}`.
Stages are the nodes of a DAG; edges connect stage **keys**. A person reviews and publishes what you write.

This copy of the skill matches schema version 2, hash `a36f6e71bcb07de2`. Pass the hash as `schemaHash` to
`validate_workflow`: when the server answers with `schemaDrift`, your copy is stale, so read the server's
`get_workflow_authoring_guide` topics (or the MCP resources) instead of these files.

## 1. When to use it

- The user wants a new workflow, pipeline, multi-stage automation, loop or fan-out in GeneratorAI.
- The user wants to change, repair or review an existing workflow (propose the change as a draft).
- The user asks to make a task repeatable, schedulable or runnable by other people or agents.

Not for running an existing workflow: for that use `list_workflows`, `describe_workflow` and `run_workflow`
(`generatorai run start` on the CLI). Workflows have no slash commands and no chat commands.

## 2. The mandatory process

Do these steps in this order, every time. Do not skip one, even for a small workflow.

1. **Inspect what exists.** `list_workflows`, then `describe_workflow` on anything close. Reuse or adapt it
   before inventing a new one; a change to an existing workflow is a draft with `replacesWorkflowId`.
   Check the agents you plan to use exist (`generatorai agent list`); if unsure, omit `agentRef` and set
   `session.model`, or ask.
2. **Draft the JSON against the schema.** Start from the closest file in `examples/` and change it.
   The schema is `schema/workflow.schema.json`; every field is in `reference/schema.md`. Every object is
   strict: an unknown or misspelled field is an error. Keep the document in a file when you have a filesystem.
   The shapes other tools use do not apply: prompts are `"prompts": [{"label", "text"}]`, the model and
   permissions go in `"session"`, dependencies are `edges`, inputs are `workflow.variables` (read as
   `{{variables.x}}`), and a loop's or map's body stages are separate `stages` entries with `parentKey`.
   Expressions (`guard`, `when`, `exits[].when`, `map.items`) are bare, never wrapped in `{{ }}`; only
   template text (prompts) uses `{{ }}`.
3. **Validate until there are zero errors.** Run `validate_workflow` (or `node scripts/validate.mjs workflow.json`
   offline, or `generatorai workflow lint workflow.json`). Each issue has `code`, `severity`, a JSON-pointer
   `path`, `message` and often a `hint`. Fix every error, then validate again. Read the warnings; fix them or
   tell the user why they are fine. Never go on with an error. After three failed rounds, re-read the
   reference topic of the failing codes (`reference/pitfalls.md` lists them all).
4. **Plan it with realistic variables and read the plan.** `plan_workflow({graph, variables})` (or
   `generatorai workflow plan workflow.json --var name=value`). Check: the stages by layer, the skipped ones,
   `unresolved` variables, codebases, post-processing, the permission mode, risk flags and warnings. If the
   plan is not what the user asked for, fix the document and go back to step 3.
5. **Summarise for the human before you submit.** In a short list or table:
   - each stage: key, kind, what it does, and what it may touch (read only, edits files, runs commands);
   - the permission mode, and any `bypassPermissions`;
   - whether the run commits, pushes or opens a pull request, and which approval comes first;
   - budgets, loop limits (`maxIterations`, exits) and map sizes;
   - the variables the user must supply and the codebases it needs.
6. **Submit it as a draft.** `create_workflow_draft({graph})` (or `generatorai workflow import workflow.json`,
   which always creates a draft). Give the user the review link and stop.

Never publish a workflow and never run a draft yourself, unless the human explicitly asks you to. Publishing
is a person's decision, in the builder or with `generatorai workflow publish <id>` from their own device.

## 3. Hard rules

- **Keys, not names.** Stage `key` is lower_snake_case (`^[a-z][a-z0-9_]{0,47}$`) and unique. Edges
  (`from`, `to`), `parentKey`, `context.from`, expressions (`stages.<key>.output`) and run overrides all use
  the key. `name` is display text only.
- **No cycles.** Repetition is a `loop` stage whose body stages set `parentKey` to the loop's key.
- **No system variables.** Never declare variables named `__…`, `repo_path_…` or `repo_branch_…`, or named
  after an expression root. A codebase path is `run.codebases.<alias>.path`.
- **Approval before a push or a pull request.** When `lifecycle.postProcessing` pushes or opens a PR, put
  `"approval": {}` on the last agent stage: a rejection fails the run, and a failed run commits nothing.
  When a stage itself pushes, deploys or opens a PR, put a `wait` stage of type `approval` before it and give
  the edge into it `"when": "stages.<wait>.output.outcome == 'approved'"` (a rejected wait completes).
- **Loops need exits and budgets.** Every loop has `exits` that read something that changes per iteration,
  a small `maxIterations` (3 to 8), and a `budget` (`maxTurns`, and `maxCostUsd` or `maxTokens`).
- **Drafts only.** You create drafts; a person publishes.
- **Command-bearing fields need `admin:settings`.** `check` stages, hooks, `onExit`/`onFailure`, `compensate`,
  `custom_script` rules, `run_script` steps, stdio MCP servers, `session.provider` and `bypassPermissions`
  make the server run programs. Add them only when the user asks, and say that saving needs an admin.
- **Secrets are `secretref:<name>`.** Never write a token, key or password into a workflow.
- **Least privilege.** Read-only stages (triage, review, research, verify) get
  `"session": {"permissionMode": "plan"}`; writers get `acceptEdits`. No `bypassPermissions` unless asked.
- **Typed handoffs.** When a later stage, guard or edge reads a field of a stage's output, give that stage
  `"output": {"format": "json", "schema": {…}}`; expressions are type-checked against it at save time.
- **Commands are literals.** `check.command` and `args` never contain `{{…}}`; pass values through `env`.

## 5. The document at a glance

```json
{
  "formatVersion": 2,
  "workflow": {
    "name": "Summarise and review",
    "description": "Summarise a topic, then review the summary.",
    "variables": [{ "name": "topic", "type": "text", "label": "Topic", "required": true }],
    "session": { "permissionMode": "plan" }
  },
  "stages": [
    { "key": "summarise", "name": "Summarise", "kind": "agent",
      "prompts": [{ "label": "summarise", "text": "Summarise {{variables.topic}} in ten bullet points." }] },
    { "key": "review", "name": "Review", "kind": "agent",
      "prompts": [{ "label": "review", "text": "Check the summary for errors and gaps. Summary:\n{{stages.summarise.output}}" }] }
  ],
  "edges": [{ "from": "summarise", "to": "review" }]
}
```

Stage kinds:

| Kind | What it is | Fields beyond the common ones |
|---|---|---|
| `agent` | An LLM agent stage | `prompts`, `followUpPrompts`, `session`, `sessionReuse`, `compactAfter`, `sessionGroup`, `context`, `output`, `retry`, `repair`, `onExhausted`, `timeouts`, `budget`, `approval`, `hooks`, `expands` |
| `check` | One deterministic command, no LLM: its exit code and output are the stage output | `check`, `retry`, `timeouts` |
| `loop` | Repeat the body (the stages whose parentKey is this key) until a rule fires | `loop`, `budget` |
| `map` | Run the body (the stages whose parentKey is this key) once per item of a runtime list | `map`, `budget` |
| `subworkflow` | Run another published workflow as this stage; its output is the child's declared outputs | `subworkflow`, `budget` |
| `wait` | Wait for an approval, an external event or a timer; the output is {outcome, data, by, at} | `wait` |

Limits:

- At most 100 stages, 500 edges and 50 variables.
- Stage keys match `^[a-z][a-z0-9_]{0,47}$`. Expressions are at most 2000 characters.
- Containers (loop, map) nest at most 3 deep; runs (sub-workflows, workflows started by agents) nest at most 3 deep.
