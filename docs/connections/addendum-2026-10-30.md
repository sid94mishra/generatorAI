## 1. What changed since 2026-10-04

### 1.1 In our code

**Nothing from the plan has been built.** No connections tables, gateway, sign-in broker or Connections page exists.

**The C1 safety gap is still live.** MCP tool calls still classify as `other`, so a Slack post or Gmail send through any
MCP server shows no Risky badge and can be approved from a phone lock screen without biometrics.
- `ToolPermissionType` is still `'file_write' | 'file_read' | 'shell_exec' | 'network' | 'other'`
  (`packages/shared/src/types/AgentMode.ts:375`).
- `classifyPermissionRisk` (`packages/shared/src/security/gateRisk.ts`) has no MCP case.

**Still unresolved:** Copilot forwards `mcpServers` (`CopilotProvider.ts:974`) while its capability flag says `false`
("Copilot SDK does not support MCP servers", `CopilotProvider.ts:1759`). No Connections boards exist yet.

**New foundations that help:**

| Since Oct 4 | Where | Use for Connections |
|---|---|---|
| Remembered permission rules (D-150): `permission_rules` table, `rememberablePermission()`, `kind: 'command' \| 'tool'` | `packages/shared/src/security/permissionRules.ts`, `packages/db/src/schema.ts` | Per-tool allow / ask / block can extend these rules instead of a new mechanism |
| Workflow event waits: `deliver_event` and a per-wait callback URL (P05), public `/workflow-callbacks` | `packages/core/src/domain/scheduler/waits.ts`, `routePolicy.ts:206` | An inbound Slack/GitHub event can resume a workflow waiting on it — a fourth event target |
| Chat-started workflow runs (`chat_workflow_runs`, v60) | `packages/db/src/migrations/v60_agent_integration.ts` | A Slack mention that starts a chat can hand off to a workflow |
| App-allowed command list with an inline "Allow" button (D-174) | `SandboxedScriptRunner.setAllowedCommands`, `PUT /settings/script-allowlist` | The same UX fits "Allow this connector tool" |
| Approval wait `onReject: fail \| complete` (D-177) | `packages/workflow-spec/src/schemas/stage.ts` | Event-driven runs can gate a send behind a person, and a reject stops the run |
| Official MCP SDK already a dependency (`@modelcontextprotocol/sdk` ^1.29) | `packages/mcp-server/package.json` | The gateway can be built on it rather than from scratch |

Latest migration is `v60`; Connections would add `v61+`.

### 1.2 In the market

- **Codex plugins** bundle skills, app connections and MCP servers into one install, shared through local or team
  marketplaces with a curated directory. Lesson: a connector should ship as a **bundle** (server + usage skill + default
  tool policy + triggers + setup guide). Our extensions API already has an unwired `registerMcpServer`.
- **Claude in Slack became Claude Tag** (2026-08-03): Claude as a shared team member in the workspace. The "bot lives in
  the app" pattern is now first-class at Anthropic.
- **Claude Code Channels** (research preview, March 2026): an MCP server pushes Telegram/Discord messages into a
  **running** session; a sender allowlist is recommended after pairing. Lesson: events must be able to *continue* a
  bound chat or thread, not only start a new one.
- **MCP events are not standardised yet.** A Triggers & Events working group exists, and SEP-2495 (server-push re-entry
  into the LLM) and SEP-2282 (server-declared hooks) are open proposals; nothing is accepted. Build our own event layer
  now, with an adapter for the standard later.
- **Slack's official MCP server** (`https://mcp.slack.com/mcp`) confirmed: internal or Marketplace apps only, no Dynamic
  Client Registration (clients that try it fail), Streamable HTTP only. Supports the "your own internal Slack app"
  model.
- **Google Workspace MCP server** appears to still be in public developer preview (one snippet of Google's May 2026 post
  conflicts).
- **Grok Connectors** launched 2026-05 with Gmail (read, draft), Calendar, Drive, Outlook, SharePoint, OneDrive, Notion,
  GitHub, Linear, later Teams, Salesforce and Box, plus custom MCP servers.

## 2. Why changes beyond today's MCP support

Today GeneratorAI is a **config forwarder**: it stores a server definition and hands it to the agent runtime (Claude
SDK, Codex app-server …), which connects. That works for:

- local servers started by a command (the 8 bundled `npx @modelcontextprotocol/server-*` entries) with a pasted token;
- remote servers that accept a fixed token header (e.g. GitHub's MCP server with a personal access token).

It does not cover what most official app servers need:

| # | Gap in today's code | What the user experiences |
|---|---|---|
| 1 | **No sign-in support.** Only static headers; no browser sign-in, callback route or token exchange. | Notion's official server can't be connected at all (browser sign-in only, no key to paste). Same for Sentry, Atlassian, Slack's official server. |
| 2 | **No token refresh.** Signed-in tokens expire, typically in 1–8 h. | A 3-hour workflow loses Notion halfway. Claude can swap servers mid-session (`setMcpServers`); Codex can't, so the run fails. |
| 3 | **Each runtime handles MCP differently.** Claude and Codex support it (Codex drops older SSE servers); Copilot, ACP and faux support none. | The same server works in a Claude chat, not in Copilot, and may vanish in Codex. |
| 4 | **Servers, not accounts.** IDs name a server (`system-mcp-slack`), not "Slack, Acme workspace". | Two Slack workspaces or two Gmail accounts collide; no work-vs-personal account per project. |
| 5 | **Every connector action is "standard" risk.** MCP calls arrive as `other`. | A Slack post or Gmail send shows no Risky badge and is approvable from a lock screen. **Live today.** |
| 6 | **No visibility into the connection.** The runtime connects, not us. | No "Connected · 23 tools · last used 2 h ago", no Reconnect, no blocking a single tool like `delete_page`. |
| 7 | **No inbound events.** MCP has no event standard yet. | A Slack @mention can't start anything. |
| 8 | **Tokens sit in each runtime's config.** | More leak surface: CLI configs, environment, process lists, logs, crash dumps. |

What each change fixes, and whether it is required:

| Change | Fixes | Required? |
|---|---|---|
| Risk classification for connector tools | 5 | **Yes, first.** Small; useful even without Connections. |
| Sign-in broker (browser sign-in, vault storage, refresh, Reconnect) | 1, 2 | **Yes.** Without it most official servers can't be used. |
| Accounts model (connector × account, grants to agents/projects/workflows/automations) | 4 | **Yes**, before a second account per app. |
| Gateway | 2 (properly), 3, 6, 8 | **A choice** — §3. |
| Event layer (Socket Mode, Discord Gateway, triggers) | 7 | Only for "an @mention starts work". Separate from MCP. |

## 3. Is the gateway needed?

The gateway is **not a new service**: one more endpoint in the existing server, built on the MCP SDK we already ship.
The agent connects to our server on loopback with a short-lived session key instead of connecting to the vendor
directly; our server attaches the real token (refreshing it when needed), checks the tool's allow / ask / block, logs the
call and forwards it.

```
today:    agent ──(Notion token)──────────────────────────────► https://mcp.notion.com/mcp
gateway:  agent ──(session key)──► 127.0.0.1/mcp/c/notion-acme ──(Notion token, refreshed)──► https://mcp.notion.com/mcp
                                   policy · audit · tool list · health
```

| | Without a gateway (sign-in broker only) | With the gateway |
|---|---|---|
| How the token reaches the agent | A fresh token goes into each session's config at start | The agent never sees it |
| 3-hour Codex workflow | Breaks when the token expires | Keeps working; we refresh behind it |
| Copilot / ACP chats | No connections | Work |
| Block one tool, tool list, health | Approval prompts only; Block not enforced on every runtime | Enforced for every runtime |
| Audit of every call | Partial | Complete |
| Cost | S–M | L |

**Recommendation:** build the sign-in broker first (needed either way), which gets Notion, Linear and Sentry working in
Claude chats quickly. Add the gateway **before workflows and automations depend on connections** — those are the long,
unattended runs where expiry and missing runtime support hurt. Rules apply in two places: approval cards in the UI (Ask)
and the gateway as a hard Block, so runtimes without approval prompts are still covered.

## 4. Plan refinements and revised phases

Changes to the 2026-10-04 plan:

1. **Safety first, on its own.** Without the gateway we only see tool names, not the servers' read-only / destructive
   hints. v0 classifies by verb — `send|post|delete|remove|update|create|write` risky or write, `get|list|search|read`
   read — plus per-server overrides; the gateway later replaces this with the real hints.
2. **See value sooner.** C0–C5 was about six phases before anyone sees a connection. First release: Connections replaces
   Settings › MCP servers, each server becomes an account, sign-in for Notion / Linear / GitHub / Sentry, per-tool
   allow / ask / block. Events, Google and Microsoft come after.
3. **Gateway in two steps:** first a token-injecting, refreshing proxy (fixes long Codex runs); then per-tool enforcement
   and audit.
4. **Four event targets, not two:** start a new chat · continue a chat bound to a Slack/Discord thread (the Channels
   model) · start an automation run · resume a workflow waiting on an event (`deliver_event`).
5. **Connectors are bundles** (the Codex model): server + usage skill + default tool policy + triggers + setup guide,
   versioned; installable through extensions later.
6. **Tighter defaults for unattended runs:** a run started by inbound content (Slack message, email) can't use
   remembered "allow" rules for write tools; automations need an explicit tool allow-list; bypass stays admin-only.
7. **Connect from desktop or web first.** Completing a sign-in on the phone needs the phone to reach the server (the
   relay), so mobile v1 is manage and approve.
8. **Workflows reference connections, not servers.** Stage tools pick `connection:<id>` + allowed tools. Shared-contract
   change: needs a D-xx.

| Phase | What ships | Size |
|---|---|---|
| **P0** | Connector tool risk: `mcp` permission kind, verb classifier, Risky badge, biometrics on mobile; resolve the Copilot MCP question | S |
| **P1** | Data model (connections, accounts, grants, tool policies); move MCP settings in; basic Connections page (list, add custom server, tool policy) | M |
| **P2** | Gateway step 1 + sign-in broker; catalogue: Notion, Linear, GitHub, Sentry, Atlassian, Slack (own app, user token) | L |
| **P3** | Events: Slack Socket Mode + Discord Gateway, the four targets, reply back to the thread, provenance labels | L |
| **P4** | Google and Microsoft (§6), polling, webhooks through a user-supplied tunnel | L |
| **P5** | Connector bundles via extensions, MCP Apps, MCP's event standard once accepted | M each |

P0 is worth doing even while the rest waits: it closes a live gap for MCP servers users can already add.

## 5. What has to be set up

### 5.1 Developer side (one-time)

**Registrations and hosting**
- A stable HTTPS domain with a homepage, privacy policy and terms. It hosts the MCP client-metadata file
  (`client-metadata.json`, the CIMD `client_id`) so open servers (Notion, Linear …) sign users in to "GeneratorAI"
  without per-vendor registration, and it is required for Google and Microsoft verification (§6).
- GitHub: reuse the OAuth app behind the existing GitHub device sign-in.
- Figma: apply to its MCP client catalogue; meanwhile personal token or Figma's local desktop server.
- Google and Microsoft app registrations and verification (§6).
- Later, optional: Slack Marketplace listing.

**Things we write and ship**
- A catalogue entry per app: server URL or command, sign-in method, default scopes, tool risk map, setup guide.
- A Slack app manifest ("Create app from manifest" pre-fills scopes, events and Socket Mode).
- A Discord invite-link generator; Google and Entra setup guides for the bring-your-own fallback.
- A **fake MCP server with fake sign-in** for automated tests (CI can't sign in to real Notion).

**Engineering**
- Migration `v61+`: connections, grants, tool policies, event sources, triggers, call log.
- Vault namespace `connection/<id>`, keeping the namespace-restricted reader invariant.
- Sign-in broker, including the desktop app's loopback callback listener.
- Gateway; risk classifier.
- Route policy: the sign-in callback and inbound event routes are public and need a security review.
- Web, desktop and mobile screens; docs-site pages.

**Test accounts (free tiers):** Slack workspace, Discord server, Notion, Linear, Sentry, a Google account, a Microsoft
account; GitHub is covered by the WORKFLOW_TEST repo.

### 5.2 Product side

- **v1 catalogue:** Notion, Linear, GitHub, Sentry, Atlassian, Slack, custom MCP. Google and Microsoft next.
- **Design boards** on the Claude Design canvas: catalogue, add flow per sign-in type, connection detail with tool
  policy, Reconnect, triggers, mobile. Prompt: [`claude-design-prompt.md`](claude-design-prompt.md) — add the four event
  targets and bundles before commissioning.
- **Defaults:** reads allowed; writes ask; send / post / delete ask and are Risky; inbound-started runs never
  auto-approve writes.
- **Honest copy:** "Tokens stay on this computer." "Slack and Discord bots only answer while GeneratorAI is running on
  this computer" — local-first means an asleep laptop is no bot.
- **Mobile v1:** manage and approve; connect later with the relay.
- **Navigation:** top-level Connections, replacing Settings › MCP servers.

### 5.3 User side, per app

| App | What the user does | Time | Admin? |
|---|---|---|---|
| Notion, Linear, Sentry, Atlassian | Connect → browser sign-in → approve | ~30 s | Atlassian: a site admin may need to allow our callback domain |
| GitHub | Connect (device code) or paste a personal access token | ~1 min | Org policy may require approving the app |
| Slack | "Create Slack app" (manifest pre-filled) → install to workspace → paste bot token (`xoxb-`) and app token (`xapp-`) → "Sign in" for MCP tools (user token, same app) | ~5 min | If the workspace restricts app installs |
| Discord | Developer Portal → New application → Bot → copy token → enable Message Content intent → invite with our link | ~5 min | "Manage Server" on that server |
| Gmail / Workspace | With our own app: Connect → Google consent → Allow. Fallback: own Cloud project, consent screen, desktop client (§6) | ~30 s / 10–15 min | Workspace admins may block third-party apps |
| Outlook / Teams (M365) | With our own app: Connect → Microsoft sign-in → Accept. Fallback: own Entra app registration | ~30 s / ~10 min | Many tenants require one admin approval |
| Figma | Paste a personal access token, or enable Figma desktop's local server | ~1 min | No |
| Any MCP server | Paste a URL (then sign in or paste a key), or enter a command | ~1 min | No |

For everyone: GeneratorAI must be running for agents to use connections and for bots to answer. Webhook-only event
sources (GitHub, Notion, Gmail push) need a user tunnel (Tailscale Funnel, Cloudflare Tunnel) — optional and later;
Socket Mode, Discord Gateway and polling need none.

## 6. Google and Microsoft: one-click sign-in

**The sign-in itself is a simple callback** (redirect → consent → code → token exchange), the same code as Notion. The
2026-10-04 plan recommended "bring your own app" only to avoid Google's app review. One-click is achievable.

**How agent apps do it:** Claude, ChatGPT, Codex and Grok each register their own app with Google and Microsoft and get it
verified; the user sees the normal consent screen and the vendor keeps tokens on its servers. We can do the same with
one advantage: Google and Microsoft both support a **desktop-app sign-in** (PKCE + loopback redirect), so the code comes
back to the app on the user's computer, which exchanges it itself. Tokens go into the local vault and never pass through
a GeneratorAI server.

### 6.1 Google

The app is reviewed at the tier of its most sensitive scope:

| Tier | Examples | Review | Cost |
|---|---|---|---|
| Non-sensitive | `drive.file` (files the user picks or the app created), `gmail.labels` | Brand check: name, logo, homepage on a verified domain, privacy policy | Free, quick |
| Sensitive | **`gmail.send`**, Calendar | + scope justification and a demo video | Free, days to weeks |
| Restricted | **`gmail.readonly`**, `gmail.modify`, **`gmail.compose`** (drafts — restricted despite the name), full Drive | + **annual security assessment (CASA)** by a Google-approved lab; restricted review ~6 weeks | Assessors set their own price; renewed every 12 months |

- **Before verification:** up to 100 users with a "Google hasn't verified this app" warning. Testing mode expires
  sign-ins after 7 days; an unverified published app avoids that but keeps the warning and the cap. Fine for a beta.
- **Refresh-token cap:** 100 per Google account per client ID; the oldest is invalidated.
- **"Local app" exemption:** older Google wording exempted device-only apps from the assessment; recent developer reports
  say Google now requires it anyway. Our agents send email content to model APIs, so data does leave the device. **Plan
  for the assessment if Gmail reading is in scope.**
- **Limited Use policy:** disclose data use; never train generalized AI/ML models on Workspace data; no human reading
  without consent. Easy for us (we train nothing), but the privacy policy must state it.
- **Workspace admins** can block third-party apps; company users may need their admin to trust our client once.
- **Google's Workspace MCP server** wants a client in the customer's own Cloud project, so with our own app we would ship
  **our own Gmail / Calendar / Drive tools** on Google's REST APIs — a connector we maintain.
- **Scope-reducing tactics:** incremental authorization (ask for restricted scopes only when a feature needs them);
  "Internal" user type when all users share one Workspace org (no review).

### 6.2 Microsoft

- One free app registration accepting work, school and personal accounts, as a **public desktop client** (no secret),
  loopback redirect.
- **Personal accounts** (Outlook.com, Hotmail): one-click immediately.
- **Work and school accounts:** depends on the tenant's consent policy. Since Microsoft's 2025 secure-by-default change
  (MC1097272, later tightened by 20 more blocked permissions), many tenants require admin consent for third-party apps:
  the user sees "Need admin approval" and an admin approves GeneratorAI once. We provide an admin-consent link.
- **Publisher verification:** free (Microsoft partner program ID + verified domain); removes "unverified" and is needed
  in tenants that allow user consent only for verified publishers. **No paid security assessment.**

### 6.3 Options and recommendation

| Option | User experience | Our effort | Where tokens and data live |
|---|---|---|---|
| A. Our own Google/Microsoft apps | One-click, our name | Google: free review for send / Calendar / Drive; ~6-week review + yearly paid CASA for Gmail reading. Microsoft: free publisher verification | **User's computer** |
| B. Rent a platform's app (Composio, Pipedream Connect, Scalekit, Nango, Arcade) | One-click, shows the platform's name ("Composio wants to access…") | Almost none | **Platform's cloud** — breaks the local-first promise |
| C. Bring your own client | 10–15 min setup | None | User's computer |

**Recommendation:**
1. **Microsoft:** our own app from the start; publisher verification. One-click for personal accounts; one admin approval
   for many work tenants.
2. **Google, staged:** our own app, unverified for early users (warning + 100 users); submit the free review for
   `gmail.send`, Calendar and `drive.file`; start the restricted review when Gmail reading is worth the yearly
   assessment. Until then Gmail reading uses option C.
3. **Keep option C as "Advanced"** for locked-down companies.
4. **Don't build on option B.** Users who want it can add the platform's MCP server as an ordinary custom connection,
   knowing their data goes through it.

**Open question for the owner:** is Gmail reading (inbox search, "new email starts an automation") needed in the first
Google release? Yes → commit to the yearly assessment. No → send, Calendar and Drive are free and one-click.

## 7. How other agent apps do it

The tedium is **Google's app review for restricted Gmail scopes**, which applies to every company. Others either pass it
or rent someone who did:

1. **Large vendors** (xAI Grok, OpenAI, Anthropic) pass Google's restricted review and yearly assessment once. Grok's
   Connectors (2026-05) read and draft Gmail, so xAI went through it; users see a normal sign-in.
2. **Small agents mostly rent a verified app** from an integration platform. Composio: "ship a Gmail integration in 30
   minutes, no Google verification on your end" — the consent screen names Composio, its quota is shared, and tokens
   live in its cloud; showing your own name means registering your own app and taking on the review.
3. **Other workarounds:** sensitive-only scopes; staying under the 100-user unverified cap; Internal apps for a single
   Workspace org; customers bringing their own client.

**Hyperagent** (Airtable's agent platform) advertises Gmail, Calendar, Slack, HubSpot and Salesforce, with schedule,
Slack-mention and email triggers. Which sign-in provider it uses could not be confirmed.

Takeaway: one-click Gmail is not harder for us than for Grok or a small startup. They passed the review or rented someone
who did. We can pass it and keep tokens local, or rent and give up local-first. Everything else in the catalogue
(Notion, Linear, GitHub, Sentry, Atlassian, most MCP servers) really is a simple callback with no review.
