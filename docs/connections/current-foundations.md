# Connections: what exists today (foundations audit)

Audit date 2026-10-04, branch `desktop_redesign`, read-only. Paths are repo-relative. Goal: a **Connections** feature
(add, authenticate, manage connectors to Slack, Gmail, Notion, Figma, Discord, GitHub, Microsoft 365; usable by agents in
chats, workflows, automations; plus inbound events such as a Slack @mention starting a chat or automation).

## 0. Headline findings

1. **GeneratorAI does not speak MCP.** It is a *config forwarder*: it decides which servers a session gets, resolves
   credentials, and hands a `Record<name, McpServerConfig>` to the harness SDK, which spawns/connects and exposes tools
   (`packages/shared/src/types/McpServer.ts` header; `packages/core/src/mcp/IMcpHub.ts` "Not in scope: launching or
   speaking to servers"). So: no MCP client, no health checks, no restart, no OAuth for remote MCP, no tool inventory.
2. **Credentials are static strings only.** MCP creds are `headers`/`env` values stored in the vault under
   `mcp/<scope>/<id>` (`McpCredentialVault`). No OAuth anywhere for third-party apps: no authorization-code, PKCE, DCR,
   RFC 9728 discovery, token refresh, or redirect/callback route. The only OAuth-ish flow is GitHub *device flow* for source control.
3. **The vault is good and reusable** (`packages/secrets`: AES-256-GCM per entry, HKDF, AAD-bound, OS-keystore KEK on desktop,
   refuse-insecure on non-loopback). It is **per server install** (one vault file next to the DB), not per user or device.
4. **An inbound HTTP webhook exists, but only for automations** (`POST /api/automations/webhooks/:token`, public route,
   token + optional HMAC `X-Signature-256`, idempotency). It is a single generic shape: no provider-specific
   verification (Slack signing secret + timestamp, Discord Ed25519, GitHub `X-Hub-Signature-256`), no URL-verification
   handshakes, no event filtering/mapping, and it can start **workflow runs only** (not a chat).
5. **Server is not internet-reachable by design.** Default bind `127.0.0.1`; LAN opt-in `0.0.0.0`; the only WAN path is the
   outbound **relay** (`apps/relay`), which carries authenticated device traffic, not third-party callers. No tunnel, no public
   URL concept, no OAuth redirect URI. Electron registers `generatorai://` but its router only knows `pair`, `command/<id>` and in-app routes.
6. **Single-user trust model.** Principals are devices/service accounts; `ownerId` and `user-session` exist as type
   placeholders ("Phase 7") with no implementation. Everything (settings, MCP servers, secrets) is server-global or project-scoped.
7. **UI foundations exist for the MCP-shaped half:** Settings → "MCP servers" on web and mobile, add-server dialogs, per-agent /
   per-stage / per-project selectors, "Effective capabilities" panel, and a Settings nav group literally named **Integrations**.

## 9. What would have to change, with risk notes

1. **DB (new migration v61+).** Add tables `connections` (id, connector_id, account label/identity, auth_kind, status, scopes, secret ref, owner, created/updated/last_used, error), `connection_grants` (connection x agent/project/workflow/automation, allowed tools), `inbound_subscriptions`/`event_triggers`, `inbound_events` (dedupe, status, payload hash, attempts). Migrations are pinned by `packages/db/src/migrations/migrations.lock.json` and frozen DDL modules (RV-33); a new `v61` module + lock entry + `schema.ts` + repository + baseline regeneration (`scripts/generate-db-baseline.ts`). Risk: medium (lock discipline). Do **not** extend `mcp-settings.json` for this; keep it as the legacy static-server store or fold it in (no-backward-compat policy lets us replace it).
2. **Secrets.** New namespace `connection/<id>` with JSON records via `setSecretJson`; refresh under a per-connection mutex; register values with `registerSecretValue`; add the missing `secret.*` and `connection.*` audit emits. Allow-list new namespaces in `McpCredentialVault`-style readers so a workflow/provider pointer can never name a connection secret (R1/R2 rules in `McpCredentialVault.ts`). Risk: high if a pointer-resolution path is widened; keep the "namespace-restricted reader" invariant.
3. **Tool assembly.** Make the hub connection-aware: extend `IMcpHub.resolveForRun` (or a new resolver feeding `resolveMcp.ts`) to expand `connection:<id>` references to `McpServerConfig` with a fresh access token (http headers) at session start; `snapshot` pointers must be `connection:` style so resume re-resolves. Long sessions outlive 1 h tokens: Claude can `setMcpServers` mid-session (`ClaudeAgentProvider.ts:3598`), Codex cannot (per-thread config), so a **local authenticating MCP proxy** (server-hosted `/mcp/connections/:id` endpoint that adds/refreshes the token and enforces per-tool policy and audit) is the provider-agnostic option and also solves SSE/Codex/Copilot transport gaps. Risk: high (new inbound surface on the API server; needs route policy entry, session-bound token, loopback-only). Verify the Copilot `mcpServers` flag contradiction first.
4. **Route policy** (`packages/auth/src/routePolicy.ts`): new `/connections` (read `read:status`? likely `admin:credentials` for write; list may use `read:status` with redaction), `/connections/oauth/callback` (public, state-bound), `/inbound/:provider/:id` (public, signature-verified; add its prefix to `WEBHOOK_RAW_BODY_PREFIXES` in `app.ts:94`). Unlisted routes fail closed to `admin:settings`, so omission is safe but breaks UX; adding `public:true` is the risky step: each must verify before any side effect and be rate-limited. Consider a `connections` scope pair (`read:connections`, `write:connections`) and add to `HIGH_RISK_SCOPES`/`MCP_FORBIDDEN_SCOPES` appropriately (MCP-device principals must never manage connections, mirroring CONVINV-R9).
5. **Permission model.** Extend `ToolPermissionType`/`classifyPermissionRisk` with `mcp` + connector metadata (server id, tool annotations, a connector-declared risk map: send/post/delete = risky), update `buildToolPermissionPayload`, both clients' gate cards (`apps/mobile/src/blocks/GateCard/model/gateModel.ts`, web gate cards), `permission-map.ts` per provider (`mcp__*` prefix -> `mcp`). Shared-contract change: needs a decision (D-xx) and cross-agent coordination with mobile. Risk: medium; high if gates regress.
6. **Triggers.** Add `event` to `AutomationTriggerType` (migration for `trigger_type` is free text, but zod `CreateAutomationSchema`, OpenAPI `openapi/spec.ts`, web/mobile wizards and `AttentionService` mapping all switch on it) with a `connectionId` + event filter; add chat target. Reuse `IdempotencyService`, `hashWebhookToken` style secrets, PD-18 bypass rule. Prompt injection risk: inbound Slack/Gmail text becomes agent input: default to non-bypass modes, mark provenance, disallow auto-approve of risky gates from inbound-triggered runs.
7. **Ingress/reachability decision (needs owner input).** Options: (a) outbound-only transports (Slack Socket Mode, Discord Gateway, Gmail users.watch + Pub/Sub pull, Graph delta queries): no public URL, fits local-first server; (b) extend `apps/relay` to a webhook ingress (public `/in/<hostId>/<connection>` forwarded over the host WS; the relay would then see third-party payloads and must verify signatures or forward opaque bodies; E2EE is not wired today); (c) user tunnel/public URL setting. (a) is the smallest security delta.
8. **Redirect handling.** Hosted callback on the relay or a fixed `https://` landing page that deep-links to `generatorai://connections/callback?...` (desktop) and universal link (mobile); loopback `http://127.0.0.1:<port>/api/connections/oauth/callback` works for desktop/web same-machine only. PKCE + `state` bound to a server-side pending record (same shape as `GitHubDeviceFlow` login ids). Update `deep-link-route.ts` allowlist for `code/state`-free completion pings (never pass tokens through links).
9. **UI.** Web: new feature `apps/web/src/features/connections/` (+ `app/routes/connections.routes.tsx`, `NAV_DESTINATIONS` entry + `nav.connections` command, `hooks/connectionQueries.ts`, ui/ kit components + stories per CLAUDE.md, brand-icon support in `ui/icons`); migrate Settings "MCP servers" into it or keep as "Advanced". Mobile: `app/(app)/connections/`, `MODULE_ROOTS`, settings index, shared `client-core` queries; must stay in step with the mobile redesign agent. Boards do not exist (D-36: no fake data; Rosetta table needs a board).
10. **Multi-user.** Out of scope unless Phase-7 `user-session` is built; decide explicitly that v1 connections are server-global and owned by the admin device, with a `created_by` field to keep the door open.

### Highest-risk items to settle first
- Token lifetime vs long-lived sessions across providers (proxy vs per-provider refresh).
- Public ingress for inbound events (Socket-Mode-style outbound vs relay/tunnel).
- MCP tool risk classification (today every connector action is "standard" and mobile-lock-screen approvable).
- Per-account identity: ids today name *servers*, not *accounts*.
- Prompt-injection from inbound content into agents with write-capable connectors.
