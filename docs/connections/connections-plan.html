Connections: bringing Slack, Gmail, Notion and the rest to every agent

A left-nav area where people connect the apps they use, so agents can work with them in chats, workflows and automations, and so a message in Slack can start work in GeneratorAI. This plan covers how other agent products do it, what we already have, the architecture we recommend, and a phased build.

01The ask

A Connections entry in the left navigation where a person adds, signs in to and manages connections to third-party apps: Slack, Gmail and Google Workspace, Microsoft 365, Notion, Figma, Discord, GitHub and more.

  • Use them anywhere an agent runs: chats, workflow stages, automations.
  • Let events start work: someone @mentions the agent in Slack, and a chat or automation starts in GeneratorAI.
  • Keep it safe: real sign-in, scoped access, approvals for risky actions, and a record of every action.

02How other agent products do it

Every one of them connects through MCP. Claude, ChatGPT and Codex, Gemini CLI, Copilot Studio, Cursor, Windsurf, Zed, Raycast, Perplexity, Grok, Manus, Make, n8n, Dust and Hermes all reach third-party apps through MCP servers. What they call "connectors", "apps" or "plugins" is a directory plus an OAuth sign-in layer on top of remote MCP servers.

Two patterns sit side by side. The Slack example needs both.

Managed integration platforms

Composio, Pipedream Connect, Merge, Zapier MCP and Arcade all hold the user's tokens in their own cloud. That conflicts with GeneratorAI running locally. Only Nango and Klavis can be self-hosted for free. People can still add any of them as an ordinary custom MCP connection, but the core shouldn't depend on them.

03What a connection actually is

Is it a bundled plugin, a deep private integration, or something anyone can use? It's three layers, and only the top one is private.

open

The app's own interface

Most large apps host an official remote MCP server (Slack, Notion, GitHub, Figma, Linear, Atlassian, Google Workspace, Microsoft Work IQ) and publish REST APIs with OAuth apps anyone can register. Discord has no official MCP server.

open, gated

The OAuth client

Anyone can register one, but each vendor decides which clients may connect. Details in the table below.

private

Directories and partnerships

What feels like deep integration in Claude or ChatGPT is mostly their directory, vendor-held OAuth clients, Figma catalogue admission and Slack Marketplace listing. OpenAI plugins bundle skills with apps; Claude Desktop extensions bundle a local MCP server with a manifest.

Notion, Linear, GitHubAny compliant client (dynamic registration or client metadata documents, PKCE)Works with our own sign-in.
SlackOnly a registered Slack app that is Marketplace-listed or internal to the workspaceDesktop-style sign-in can't get bot permissions. Socket Mode apps can't be Marketplace-listed. Distributed non-Marketplace apps get 1 request a minute on channel history; internal apps are exempt.

Five foundational changes

  1. Our own MCP gateway (client and proxy) instead of forwarding raw configs.
  2. An OAuth broker and token records with refresh, issuer checks and reconnect prompts.
  3. Risk classes for connector tools (read, write, send/delete) wired into gates and signed approvals.
  4. Connection identities (app × account) with access grants to agents, projects, workflows and automations.
  5. Event intake: event sources, then triggers, then a chat or automation, starting with outbound connections.

Core concepts

  • Connector: a catalogue entry. Name, icon, MCP address or command, sign-in method, default permissions, tool risk map, events it can send, setup guide. A custom MCP server is a connector too.
  • Connection: one signed-in account of a connector. Account name, status (Connected, Reconnect needed, Error, Off), permissions, who created it, last used.
  • Access grant: which agents, projects, workflows and automations may use a connection, and with which tools.
  • Tool policy: Allow, Ask or Block per tool. Reads default to Allow, writes to Ask, sends and deletes to Ask and are marked Risky.
  • Trigger: an event from a connection, with a filter, mapped to a new chat (agent, project, permission mode, reply in the thread) or an automation run.

Why a gateway, not "give the token to each provider"

OptionVerdictWhy
Put the token in each provider's MCP config (today's static headers)noTokens expire in 1–8 hours while sessions run longer; Codex can't swap servers mid-session; Copilot and others don't support MCP; tokens land in CLI processes and logs; no shared approvals or audit.
Let each provider CLI sign in itselfnoTokens split across tools, no shared catalogue, no access grants, no events, nothing on mobile.
A GeneratorAI gatewayrecommendedOne MCP client we control: transparent refresh, tokens stay in our vault, per-tool policy and risk, every call recorded, same behaviour for every provider, health and tool lists for the UI. Matches the MCP spec's rule that servers never pass tokens through.

06Sign-in and safety

Sign-in, to the current MCP spec (2026-07-28)

  • Discovery and checks: protected-resource metadata, then server metadata; resource indicators; PKCE (refuse servers without it); state; issuer validation with credentials tied to their issuer. Missing issuer checks were the bug in the 28 Sept 2026 MCP Python SDK advisory.
  • Client registration order: pre-registered, then a client metadata document (one static HTTPS file we host, as Claude Code does), then dynamic registration as a fallback, then a client ID the user enters.
  • Where sign-in returns:
    • Desktop: a local port on this machine.
    • Web on the same machine: the server's own callback.
    • Phones and remote web: the system browser, finishing on the server; only a tokenless "done" signal travels by deep link.
  • Refresh: 5 minutes before expiry and again on a 401, one refresh at a time per connection, saving rotated tokens safely. If refresh fails, the connection shows "Reconnect needed" and an Activity card asks you to reconnect.
  • Address safety: HTTPS only, private network ranges blocked during discovery, sign-in pages never opened through a shell (the cause of CVE-2025-6514).

Approvals and prompt injection

  • Gate cards name the app and the action, e.g. "Post to #releases in Acme Slack". Risky actions need the Face ID-signed approval on mobile, like shell commands today.
  • Untrusted input never auto-approves a write. A run started by a Slack message or an email never auto-approves a write or send. Automations get an explicit tool allowlist, since nobody is there to approve. "Bypass permissions" stays admin-only and is never the default for event-started runs.
  • No remote images or links rendered automatically from connector output. That was the exfiltration path in the Slack AI and AgentFlayer incidents.
  • Everything is logged: connections created, authorised, refreshed, revoked; every tool call with its approver; every inbound event received or rejected.

The Slack example, end to end

  1. Connections › Add › Slack opens a guided setup.
  2. We generate a Slack app manifest. The person creates it in their workspace as an internal app: no Marketplace review, and no history rate cap.
  3. They paste the bot token and the app-level token. Optionally they also connect Slack's own MCP tools with their user account.
  4. The server opens a Socket Mode connection. No public address is needed.
  5. Someone writes "@GeneratorAI why is checkout failing?" and a trigger starts a new chat with the chosen agent and project, bound to that Slack thread.
  6. The agent works. Its replies post back to the thread, and risky actions still ask.
  7. The run appears in the Activity column as "From Slack · #support · @maya".

This is the model Hermes Agent uses. A Marketplace-listed GeneratorAI Slack app would need webhooks and a relay, so it's a later option.

09The Connections page

  • Left nav "Connections" on web, desktop and mobile, plus a command in the palette and the desktop menu.
    • Catalogue: featured apps, categories, and "Custom MCP server".
    • My connections: account, status, who uses it, events, last used.
    • Connection detail: account and permissions, tools with Allow / Ask / Block, access, events and triggers, an activity log, reconnect and disconnect.
  • Settings › MCP servers folds into Connections. Existing servers are migrated once, then the old screens are removed.
  • Pickers in the agent editor, workflow stage tools, chat composer and project settings choose connections and tools, not raw servers.
  • The Activity column shows "Reconnect Slack" and "This agent wants to use Gmail" asks, and labels runs started by events.
  • Boards come first. The design rule is no screens without data, so the boards are commissioned before the UI phase. The prompt is in section 14.

12Why this approach

  • MCP first, because it's what the whole industry uses and the big apps host their own servers. Every connector we don't write is maintained by the app's vendor.
  • Our own gateway, because it's the only option that keeps tokens away from model-facing processes, behaves the same for every provider, survives token expiry in long runs, and gives one place for approvals and audit.
  • Tokens on your machine, with "bring your own app", because GeneratorAI is local-first and single-owner. Managed platforms take custody in their cloud. The same trade is made by Hermes Agent, Raycast (its own credentials for Slack) and Claude Code.
  • Outbound connections before webhooks, because they need no public address or relay and they cover the flagship case: Slack and Discord mentions.
  • Safety before breadth, because the incident record is about connector data driving write tools (GitHub MCP, Slack AI, AgentFlayer), and our MCP actions are unclassified today.

Rejected

  • Building on Composio, Pipedream or Merge: tokens in their cloud, per-call pricing.
  • One hand-written integration per app: high upkeep, and it duplicates the vendors' own MCP servers.
  • A hosted relay as the default for events: breaks local-first, and today's relay isn't end-to-end encrypted.
  • Multiple users now: no user model exists yet. Version one is per server, with a "created by" field to keep that door open.

WHAT CONNECTIONS IS
Connections let a person connect GeneratorAI to the third-party apps they already use — Slack, Discord, Gmail and Google Drive, Outlook and Teams, Notion, Figma, GitHub, Linear, Jira and Confluence, Sentry — or to any MCP server. Agents then use those apps as tools in chats, workflow stages and automations. Some connections can also start work: when someone @mentions GeneratorAI in Slack, a new chat (or an automation run) starts and replies in the same Slack thread.

Everything runs on the person's own machine: tokens stay in the local vault and never reach the model. Every tool a connection offers has a risk class:
- Read — allowed by default.
- Write — asks by default.
- Send / post / delete — asks and is marked Risky. On a phone it needs Face ID.
Each tool can be set to Allow, Ask or Block.

Connections authenticate in three ways, and the boards should make the difference clear without jargon:
1. Sign in — OAuth in the system browser (Notion, Linear, GitHub, Atlassian, Sentry).
2. Your own app — a guided setup where the person creates an internal app in their own Slack workspace, Google Cloud project or Microsoft tenant and pastes the credentials. It's needed because those vendors only let registered apps connect, and it keeps the data private.
3. Token or key — Discord bot token, Figma personal token, API keys, or none, for a custom MCP server.
