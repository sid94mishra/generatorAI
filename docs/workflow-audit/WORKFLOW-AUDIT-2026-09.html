Workflow Engine Audit and Improvement Plan

Branch desktop_redesign @ a83a7bf Date 24 Sep 2026 Scope ~52k lines across core, db, server, web, cli-core, sdk, shared Status for review

Executive summary

The workflow module is broad and much of its design is right. It has a declarative DAG, a pinned topology snapshot, a durable turn journal, a crash-recovery path, a replayable multiplexed stream and a polished run page.

Live runs confirm the scheduler logic is correct: joins, conditions with AND/OR/NOT, skip cascades, all four edge types, retry backoff, approve and reject, and a 25-stage DAG all behaved as specified. The stage executor is where the problems are. Pausing, "request changes" on an approval, crash recovery and result validation all produced wrong output that the run still reported as completed.

Beyond the executor:

  • A stage that re-enters running after an approval or a validation retry is reaped as stale.
  • Success criteria are checked against the model's summary turn as well as its answer.
  • The same workflow commits and opens a PR when launched from the web, and silently does not when launched from the CLI or an automation.

Almost every defect traces back to three structural patterns, not to isolated mistakes:

  1. One field, six hand-written mappings. A stage option has to be carried through the zod schema, the service, the repository, the DB column, the web toStageParams, the exporter, the importer and three script materializers. Each earlier fix patched some layers and missed others. The result is roughly 20 options that are stored-but-ignored, accepted-but-dropped, or impossible to clear.
  2. State transitions are unconditional writes, and ordering is left to chance. Stage and run status changes are plain UPDATEs, not compare-and-set. Terminal events go to a channel the run never listens on, so a 3-second reconciler does all the routing and hides the races. Abort-before-write, reaper-vs-resume and double-finalize bugs all come from this.
  3. Two lifecycles for one run. WorkflowOrchestrator (clone, preprocess, uploads, commit/PR) wraps WorkflowRunService only for some entry points. CLI, automations, SDK run(), MCP, scripts and retries skip it. Behaviour depends on the caller.

The plan in Part V fixes the patterns rather than the symptoms, in four phases:

  • Phase 0 (about 2 weeks). Targeted fixes for the P0s and the security issues.
  • Phase 1 (about 5 weeks). One schema-derived mapping, an atomic versioned graph save, runs pinned to immutable definition versions, CAS state transitions with an event-driven per-run scheduler, and a single run lifecycle.
  • Phase 2. The capabilities modern engines treat as standard: rerun-from-stage, error classes with pause-on-exhaustion, split timeouts, typed outputs with a repair turn, join policies, loops, fan-out, budgets and tracing.
  • Phase 3. Differentiators such as run diffing and pinned-data stage testing.

There are two ways into a run, and they are not equivalent. The orchestrated path is POST /orchestrator/runs → WorkflowOrchestrator.execute. It is used by the web when the definition has orchestratorConfig or the user uploaded files, and by mobile and SDK orchestrate(). It adds these phases around startRun:

  • workspace and worktree creation, and repository clone;
  • project config wiring and preprocessing steps;
  • an upload scan (skills, agents, prompts) and a sandbox;
  • post-processing: autoCommit, autoPush, autoCreatePR.

The plain path is POST /workflow-runs + /start. It is used by the CLI, automations, SDK run(), the MCP server, script runs and every retry, and it skips all of those phases (WorkflowOrchestrator.ts:589-744,903-982).

"Orchestrated mode" is not an orchestrator agent. The LLM orchestrator, which spawns workers through tools (OrchestratorService), is bound only to chats (ChatManagementService.ts:1994-2011). A stage bound to an orchestrator-role agent gets its team as SDK sub-agents (SES:444-452), and on Codex, OpenCode and ACP those are dropped.

Definition model

WorkflowDefinition

name, description, version (bumped only by a definition PATCH, never compared), sessionMode (auto/single/per-stage, default auto), harnessConfig (model, harnessType, reasoningEffort, maxTurns, permissionMode, systemMessage, mcpServers, tools allow/deny, skills, customAgents, BYOK provider, agentRef), variables[] (string/number/boolean/choice/text, ≤50), tags, hooks[] (15 phases), hooksFile, projectId, orchestratorConfig (codebaseAliases, preprocessing/post-processing steps, resultValidations by stage index, requiresCodebase, autoCommit/Push/CreatePR). Also declared but not stored or not read: skills, agents, defaultAgentRef, useWorktree, browserConfig, selectedArtifacts.

StageDefinition · StageEdge

A stage has prompts[] (label, text with {{var}}, waitForCompletion, attachments), harnessConfigOverrides, agentRef, agentMode (auto/plan), condition, retryPolicy, timeoutMs, contextFilter, contextSources, outputFormat/outputSchema/expectedOutput, resultValidation[], approvalRequired, hooks[], variables and iterationConfig. An edge is (from, to, edgeType), with edgeType one of on_success, on_failure, on_completion or always. The DB enforces UNIQUE(from,to) regardless of type. Edges carry no condition, although the builder API and the CLI docs suggest one.

Tables (packages/db/src/schema.ts:378-619): workflow_definitions, stage_definitions (cascade on definition), stage_edges (cascade on both), workflow_runs (definition_snapshot, agent_snapshot, ancestor_run_id), stage_runs (version, heartbeat_at, lease_owner, wake_at; FK to stage_definitions without cascade), plus the durable journal (register and entries), session_allocations, stage_session_maps and stream rows. Foreign keys are enforced (db/src/index.ts:334). There is no soft delete and no optimistic lock on definitions.

Run lifecycle

  1. Create. createRun (WRS:408-579) freezes definitionSnapshot (stages and edges), type-checks variables, fills in defaults, and inserts the run plus N pending stage rows in one transaction.
  2. Start. startRun (WRS:675-864) provisions a workspace or worktree, sets starting, fires on_run_start and builds the DAG from the snapshot. It resolves auto to single for a linear DAG, else per-stage. It then sets running, subscribes to global events, starts the 3 s reconciler and calls advanceRun.
  3. Schedule. advanceRun → reconcileRun (per-run FIFO lock) → a pure reconcileDAG, which returns {toLaunch, toSkip, runTerminal}. Each launch goes through admission, the semaphore and executeStage, fire-and-forget.
  4. Execute. executeStage (SES:1035-2734):
    • claims pending→queued atomically and resolves the agent;
    • runs pre_run hooks, allocates a session, sets running and starts the heartbeat;
    • runs its turns through the durable effect journal: context turn, prompt turns, output-format retries, summary turn;
    • persists artifacts, runs post_run hooks and the optional approval gate;
    • writes completed and emits stage_run.completed on the session channel.
  5. Advance. Because the run subscribed to the global channel, it never sees that event. The 3 s reconciler notices the completed row, runs result validation (onStageCompleted), may retry, then calls advanceRun.
  6. Finish. finalizeRun → completeRun releases sessions, completes the workspace and fires on_run_complete. On the orchestrated path, a listener then runs commit, push and PR.

Controls.

  • Run: pause, resume, cancel, retry. Retry creates a new run with ancestorRunId and copies the completed stages.
  • Stage: pause, resume, retry, cancel, interrupt, approve, reject, request changes, wake.

Only startRun uses the run state machine. Every other transition is a raw status write. The stage state machine is checked after the DB write, as an assertion.

Sessions and context passing

  • Session modes. per-stage gives each stage its own session. single shares one session: the first stage creates it with its own model, agent, tools and permission handler, and later stages only resume it. auto becomes single for any linear DAG, and auto is the default.
  • Context between stages. gatherPredecessorSummaries takes contextSources (stage names) or the direct predecessors, and injects them as a separate internal user turn according to contextFilter: summary-only (the default; an LLM summary turn, or the first 3000 characters as fallback), full, structured (summary plus outputData), or none.
  • Templating. {{name}} and dotted paths over run variables and hook-injected variables. Stage outputs cannot be referenced in prompts or in conditions.
  • Workspace. A per-run workspace, or git worktrees per project codebase. A retry strips the workspace variables and starts in a fresh, empty directory.

Conditions, success criteria, retry and timeouts

Condition grammar

expr  := or ; NOT > AND > OR, parentheses
ops   := AND OR NOT (word-boundary) | && || !
leaf  := true | false | lhs (== != < <= > >=) rhs
value := 'str' | "str" | number | status | parentStatus
       | variables.a.b

The only scopes are the activating parent's status and static run variables. There is no access to a stage's output. Equality is loose. An unresolvable operand becomes undefined, and undefined == undefined is true. NOT alone evaluates to true.

Result validation (success criteria)

Rule types: contains, not_contains, min_length, max_length, regex (no ReDoS guard), custom_script (a host shell command with a 60 s timeout), json_schema (top-level keys of the first json block) and llm_validation. The last is a placeholder that only checks length ≥ 50.

Input is every assistant message of the stage's session. Validation runs only inside the reconciler tick. On failure there is an in-session retry for early attempts and a full restart for the last; the backoff sleep happens inside the tick. The validation retry default is 0, the error retry default is 1 ({1, 3000 ms, ×1}), and there is no error classification.

Timeouts.

  • The per-prompt timeout (default 300 s) covers only the main prompt turns, and it includes time spent waiting for a human tool approval.
  • Context, summary, output-retry, recap, in-session-retry and follow-up turns have no timeout.
  • The heartbeat is a 10 s setInterval, and the reconciler fails rows whose beat is older than 30 s. That measures whether the process is alive, not whether the stage is making progress.

Durability and crash recovery

Each turn is an effect: intent is written, the turn runs, and settlement is written in one transaction. After a crash, settled turns replay from the journal without re-running. For an in-flight turn:

  • If its policy is safe (only read or web tools), it re-runs.
  • If its policy is never (any write, shell or browser tool, which is almost every stage), it is skipped with a synthetic result and the stage continues to completed.

On boot, running stages are reset to pending and the run is re-driven. That happens before the session allocator rehydrates. awaiting_input stages stay parked, and DurableSleepService is sound but nothing calls sleep().

Thought experiment: server killed with three parallel stages in flight. On reboot, all three are reset and relaunched. Their completed turns replay for free. The interrupted turn on each mutating stage is skipped, so each stage "completes" on partial work, possibly with empty output, and its successors run on that. Nothing is double-executed on this path. Double execution comes instead from the cancel, reaper and route-retry races (W-01, W-02, W-12). Confirmed live (T8): there was no double execution and no hang, but even a turn that had finished 12 s before the kill was treated as in flight and skipped, and the stage completed with empty output (W-16).

Streaming

Transport and replay:

  • EventBus.emit(sessionId) commits through StreamBroker, then broadcasts. A bridge republishes every event that carries workflowRunId into the run scope, fire-and-forget.
  • The client opens one multiplexed EventSource per tab and subscribes to run:<id>. It hydrates by paging streamReplay 500 rows at a time and buffers live frames during replay.
  • Deltas may be dropped under congestion (announced with a gap frame). Items are never dropped by design.
  • Stage transcripts live in messages.

Event catalog.

  • Run: workflow_run.{created, starting, running, paused, resumed, cancelling, cancelled, completed, failed, retried, permission_mode_changed, stage_validation, orchestration_*, preprocessing_*, postprocessing_*, worktree_creating, sandbox_*}.
  • Stage: stage_run.{queued, running, step_started, step_completed, completed, failed, skipped, retrying, awaiting_input, input_received, sleeping, woken}.
  • Harness: harness.* deltas, tools, usage and session info.
  • Hooks: hook.*.

A user-initiated stage_run.cancelled or stage_run.paused is never emitted.

Write cost:

  • Each token delta is written twice: once to the session scope and once to the run scope.
  • Each stage costs roughly 25–40 writes, plus a heartbeat every 10 s.
  • Each active run costs about 2–6 reads every 3 s for its whole lifetime, including 30-day approval waits.

Import from JSON, export and templates

Import validates edge indices, then creates the definition, stages (through the shared templateStageToCreateParams) and edges in one transaction, validating the DAG after each edge. Cycles, self-edges and duplicate pairs roll the whole import back. Unknown keys are stripped silently. There is no format version. Duplicate names are accepted.

Export (GET /:id/export) returns a template-shaped object, not an import-shaped one. CLI clone is export → import, so it inherits every gap.

Round trip.

  • Survives: the core stage fields and the edge types.
  • Lost: stage agentMode (a plan-gated stage comes back as auto), iterationConfig, the whole orchestratorConfig (project, codebases, auto-commit and PR, preprocessing, workflow-level validations), projectId, skills, agents, defaultAgentRef, hooksFile, browserConfig.

Templates. Four of the five system templates cannot be imported as JSON. e2e-testing-workflow.json still uses the pre-June key copilotConfig, so its model and system prompt are stripped.

How the live results relate to the static findings. The runtime probe predicted that cancel would bring a stage back. Live, on claude-agent, an aborted prompt resolves instead of throwing, so the stage runs its summary turn and ends completed with empty output. The scheduler-hop latency predicted by the static audit (W-08) was measured at 1.6–2.8 s per hop, which is real but small next to model time.

Part III · Audit findings

Root-cause patterns

1 · Hand-carried fields

Every stage or definition field crosses 6–10 hand-written mappings: the zod schema, the service entity literal, the repository create/update/mapRow, the DB column, web toStageParams, the exporter, the importer, the template schema and three script materializers. A missed layer silently drops, strips or freezes the value.

About 20 register entries come from this. So did five of the eight September fixes, which reopened because they patched only some layers.

2 · Unconditional transitions, accidental ordering

Status writes are plain UPDATEs. Abort happens before the terminal write. Stage terminal events go to a channel the run does not hear, so a 3 s single-threaded tick serialises everything by accident.

This produces resurrection on cancel, the reaper killing live stages, lost dedup keys, double finalisation and slow hops. Fixing the routing without adding CAS would expose more races.

3 · Split lifecycle

Pre- and post-processing, uploads, the sandbox and SCM live in WorkflowOrchestrator. The workspace, DAG and hooks live in WorkflowRunService. Six entry points bypass the first.

The result: missing PRs, missing browser tools, hooks that fire twice, and a retry that runs in an empty folder.

4 · Controls with no reader

These controls are stored but have no run-time reader:

  • stage variables, prompt files, template select, stage skills;
  • iterationConfig, durable sleep, defaultAgentRef, codebaseAliases;
  • post-processing enabled, the Widget tab, the stage "…" button;
  • llm_validation, legacy webhooks.

Users configure them and nothing happens.

Part IV · Benchmark against modern engines

GeneratorAI is a declarative DAG interpreter whose nodes are expensive, non-deterministic agent sessions. That places it with DBOS, Inngest, Cloudflare Workflows and LangGraph. All of them memoize each step's result and skip completed steps on recovery. It does not belong with Temporal-style replay of orchestrator code. The right durability primitive is memoized stage results keyed by (run, stage, iteration), plus a pinned definition snapshot. GeneratorAI already has most of the pieces: the turn journal and definition_snapshot. What is missing is using them consistently.

Documentation drift

.github/docs/feature-workflows.md, feature-stages.md and feature-workflow-runs.md diverge from the code in more than 25 places. The ones that mislead users:

  • Wrong verbs and routes. Stage update is documented as PATCH but is PUT. POST /from-template/:id does not exist; the real route is POST /import {templateId}.
  • Fictional SDK example. The §7 example in feature-workflows.md calls workflow(), .profile() and .resultValidation(), none of which exist.
  • Features documented as working that are not. Stage variables and file prompts are described as working (both are dead). "Renaming a stage does not break anything" is false: contextSources match by name.
  • Wrong semantics. on_success is described as requiring all predecessors (it is any activating parent). Both retry defaults are documented as {1, 3000, 1}, but validation retries default to 0.
  • Wrong CLI and config. edge add --condition is documented but edges have no condition. --timeout is documented in ms but takes seconds. GENERATORAI_ORCH_WORKER_TIMEOUT_MS is described as a wall-clock kill; it only bounds check(wait).

Recommendation: generate the field reference from the zod schemas (Phase 1.1 makes this free). Keep hand-written docs for semantics only.
