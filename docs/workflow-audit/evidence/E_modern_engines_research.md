# Modern Workflow and Agent-Orchestration Engines (2025–2026): Benchmark for GeneratorAI

Research date: 2026-09-24. Sources are official docs wherever possible; third-party sources are marked **[3p]**. Each claim carries a link. "Not verified" means I did not find a primary source during this pass, not that the feature is missing.

GeneratorAI baseline (from the brief): a local-first, SQLite-backed TypeScript platform. A workflow is a DAG of **stages**, and each stage is an LLM-agent session (Claude Agent SDK, Copilot SDK or Codex). Each stage has a prompt, skills, MCP servers, edge conditions (`on_success`, `on_failure`, `on_completion`, `always`), a retry policy, a timeout, result-validation rules, human approval gates, hooks and durable sleep. An optional **orchestrator-agent** mode controls workers dynamically. Underneath is a `DurableExecutionEngine` (steps, effects, leases, replay), and the web UI streams agent output.

---

## 0. Top findings for GeneratorAI (TL;DR)

1. **Use step memoization, not event-sourced replay.** GeneratorAI's control plane is a *declarative DAG*, and its stages are *non-replayable LLM sessions*. That puts it in the same family as DBOS, Inngest, Cloudflare Workflows, Absurd, Vercel WDK and LangGraph: checkpoint each stage's output and skip completed stages on recovery. It does not need Temporal-style history replay of orchestrator code ([DBOS architecture](https://docs.dbos.dev/architecture), [Inngest execution](https://www.inngest.com/docs/learn/how-functions-are-executed), [Cloudflare rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)). Determinism is then mostly a *definition-pinning* problem.
2. **Pin every run to the definition version that started it.** Airflow 3, Trigger.dev, Vercel WDK, Temporal (Pinned) and DBOS all do this. Snapshot the DAG, prompts, skills and MCP config into the run row. Editing a template must never change an in-flight run ([Airflow 3 notes](https://airflow.apache.org/docs/apache-airflow/3.0.0/release_notes.html), [Trigger.dev versioning](https://trigger.dev/docs/versioning), [Temporal Worker Versioning](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning)).
3. **"Rerun from step / fork" is now table stakes, and it is the main debugging tool for LLM workflows.** It appears as Inngest *Rerun from step* with edited input, DBOS `forkWorkflow`, Mastra `timeTravel`, LangGraph replay/fork, Step Functions *redrive*, Temporal *reset* and n8n *debug in editor*. Earlier stage outputs become memoized state, so later stages re-execute without re-paying for earlier LLM calls ([Inngest rerun](https://www.inngest.com/docs/platform/manage/rerun-function-runs), [DBOS forks](https://www.dbos.dev/blog/handling-failures-workflow-forks)).
4. **Exhausted retries should pause, not fail.** Restate 1.5 now *pauses* invocations when retries run out and lets you resume them on a newer deployment ([Restate 1.5](https://restate.dev/blog/announcing-restate-1-5)). For expensive agent runs this beats "fail and start over".
5. **HITL is a durable wait with a correlation key and a timeout, and it must not hold a worker slot.** See Inngest `waitForEvent` (returns `null` on timeout), Trigger.dev waitpoint tokens (callback URL plus idempotency key), Step Functions task tokens plus heartbeat, and Airflow 3.1 deferrable HITL operators.
6. **Flow control belongs in the engine.** That means concurrency caps per key, throttling, priority, fairness, debounce and singleton ([Inngest flow control](https://www.inngest.com/docs/guides/flow-control), [Hatchet concurrency](https://docs.hatchet.run/v1/concurrency), [Temporal priority/fairness](https://docs.temporal.io/develop/task-queue-priority-fairness)). For a local-first app, the key uses are per-provider/per-model concurrency and a global agent-session cap.
7. **LLM-specific engines converge on the same set of features.** Each step gets typed input/output schemas (Mastra), scorers or evals sampled per step (Mastra), a model fallback chain (Mastra), guardrail tripwires that block or run in parallel (OpenAI Agents SDK), `maxTurns`/`maxBudgetUsd` caps (Claude Agent SDK), and OTel GenAI spans `invoke_agent` → `chat` → `execute_tool` with `gen_ai.usage.*` tokens.
8. **Anthropic's own guidance.** Multi-agent systems use about **15× the tokens of chat**. Stateful errors compound, so you need resume-from-failure, not restart. Rainbow-deploy so running agents are not disrupted. Pass *artifacts* (files) between agents instead of relaying everything through the coordinator ([multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Evaluator-optimizer and orchestrator-workers need explicit stopping conditions ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)).
9. **SQLite is a first-class durable-execution substrate.** DBOS Python *defaults* to SQLite ([config](https://docs.dbos.dev/python/reference/configuration)). DBOS Go added SQLite in June 2026 ([DBOS news](https://www.dbos.dev/blog/new-in-dbos-june-2026)). Cloudflare Workflows persist every step transition in a Durable Object's SQLite ([CF blog](https://blog.cloudflare.com/building-workflows-durable-execution-on-workers/)). LangGraph and CrewAI ship SQLite checkpointers. Litestream 0.5 gives PITR and replicas.

## 1. Durable execution models: a taxonomy

| Model | How it works | Engines | Implication |
|---|---|---|---|
| **Event-sourced replay of orchestrator code** | Every command/result is appended to an event history. On recovery the workflow function is re-run from the start, and recorded results are fed back in. Code must be deterministic. | Temporal ([determinism/sandbox](https://docs.temporal.io/develop/typescript/workflows/basics), [event history](https://docs.temporal.io/workflow-execution/event)), Restate journal ([ctx.run journaled](https://restatedev.github.io/sdk-typescript/interfaces/_restatedev_restate-sdk.Context), [building blocks](https://docs.restate.dev/concepts/durable_building_blocks/)), Hatchet durable tasks ([durable event log](https://docs.hatchet.run/home/durable-execution)), AWS Lambda durable functions ([checkpoint and replay](https://docs.aws.amazon.com/lambda/latest/dg/durable-functions.html)), Vercel WDK ([event log, deterministic replay](https://vercel.com/blog/introducing-workflow)) | The most expressive model: arbitrary code, signals, dynamic control flow. The cost is determinism rules, patching and history limits (Temporal: 51,200 events / 50 MB, [limits](https://docs.temporal.io/workflow-execution/limits)). |
| **Step memoization (re-invoke and skip)** | The handler is re-invoked. Each completed step's output is looked up by a *step ID* and returned instead of re-executing. | Inngest ([re-runs handler per step, step ID hashed](https://www.inngest.com/docs/learn/how-functions-are-executed)), Cloudflare Workflows ([step name is the cache key](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)), DBOS ([one DB write per step checkpoint](https://docs.dbos.dev/architecture)), Absurd on Postgres ([steps are checkpoints](https://lucumr.pocoo.org/2025/11/3/absurd-workflows/)) | Simple, cheap and database-native. Step IDs must be deterministic. Code outside steps re-runs. **Best fit for GeneratorAI.** |
| **Superstep / graph checkpoints** | State is snapshotted at each superstep boundary (plus per-node pending writes). | LangGraph ([durability modes exit/async/sync, per-task writes](https://docs.langchain.com/oss/python/langgraph/durable-execution)), Microsoft Agent Framework ([checkpoint at end of each superstep](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)), Mastra snapshots ([snapshots](https://mastra.ai/en/reference/workflows/snapshots)), CrewAI `@persist` to SQLite ([Flows](https://docs.crewai.com/en/concepts/flows)) | Natural for graph-of-agents systems, and gives time travel almost for free. Durability depends on the checkpoint mode. [3p critique: MAF checkpoints only at superstep boundaries](https://www.diagrid.io/blog/still-not-durable-how-microsoft-agent-framework-and-strands-agents-repeat-the-same-mistake). |
| **Declarative state machine / DAG interpreter** | The engine interprets a JSON/YAML definition and persists per-state results. | AWS Step Functions ([states](https://docs.aws.amazon.com/step-functions/latest/dg/workflow-states.html)), Argo, Airflow, Serverless Workflow DSL ([dsl-reference](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)), n8n | No determinism burden on user code. Versioning means pinning the definition. **This is what GeneratorAI's DAG is.** |

**Takeaway.** GeneratorAI is a *declarative DAG interpreter* whose nodes are expensive, non-deterministic agent sessions. The right durability primitive is **memoized stage results keyed by (run_id, stage_id, attempt/iteration)**, plus a **pinned definition snapshot**. Replay applies only to the scheduler's own decisions, which are pure functions of the pinned DAG and the recorded stage results. Inside a stage, the closest analogue to Temporal's "LLM calls as activities" is the Temporal and OpenAI Agents SDK integration. There, the agent loop runs in the workflow and each model call and tool call is a durable activity ([Temporal OpenAI Agents integration](https://docs.temporal.io/develop/python/integrations/openai-agents)). For Claude/Copilot/Codex harnesses, the practical equivalent is to persist the harness session ID plus the streamed transcript so a crashed stage can be *resumed* rather than restarted.

## 3. Best-practice catalog

Each entry gives **What** it is, **Who** does it (with citations), **Why** it matters, and **For GeneratorAI** what to check or build.

### A. Durability, idempotency, determinism

**A1. Checkpoint each unit of work's result and skip it on recovery (step memoization)**
- *What:* Persist each step's output. On restart, replay returns stored outputs until it reaches the first step with no checkpoint.
- *Who:* DBOS: "if there is a checkpoint, the step returns the checkpointed output instead of executing", at the cost of "one database write per step" ([DBOS architecture](https://docs.dbos.dev/architecture)). Inngest: memoized step state keyed by a hashed step ID ([execution](https://www.inngest.com/docs/learn/how-functions-are-executed)). Cloudflare: state returned from each `step.do` is persisted ([sleeping and retrying](https://developers.cloudflare.com/workflows/build/sleeping-and-retrying)). Restate: journals every `ctx.run` ([Context](https://restatedev.github.io/sdk-typescript/interfaces/_restatedev_restate-sdk.Context)). Absurd: "Once a step completes successfully its return value is persisted and the step won't execute again" ([Absurd](https://lucumr.pocoo.org/2025/11/3/absurd-workflows/)).
- *Why:* LLM stages are slow and expensive. Recovery must never re-run a completed stage.
- *For GeneratorAI:* The key should be `(run_id, stage_id, iteration/fan-out index)`. Mastra hit exactly this bug: "Durable workflow operation IDs collide across loop iterations and resume executions" ([mastra#24044](https://github.com/mastra-ai/mastra/issues/24044)). Foreach iterations need a per-index suffix ([mastra#24581](https://github.com/mastra-ai/mastra/issues/24581)).

**A2. Deterministic step identity; no side effects outside steps**
- *Who:* Cloudflare's "Rules of Workflows": name steps deterministically, never with a date or randomness. Wrap side effects in steps. Don't rely on in-memory state outside steps. Base conditions only on event payload or step outputs. Always `await` steps. Wrap `Promise.race` in a step ([rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)). Temporal's TS sandbox replaces `Math.random`, `Date` and `setTimeout` with deterministic versions ([workflow basics](https://docs.temporal.io/develop/typescript/workflows/basics)). DBOS: the "workflow function must be deterministic" ([architecture](https://docs.dbos.dev/architecture)). Vercel WDK runs `"use workflow"` code in a sandboxed VM ([3p skill summary](https://mcpservers.org/agent-skills/vercel/workflow/workflow)).
- *Why:* Otherwise recovery takes a different branch and memoized results end up attached to the wrong step.
- *For GeneratorAI:* Edge-condition evaluation (`on_success`, `on_failure`, AND/OR expressions) must be a pure function of recorded stage results. It must never re-read live state such as files or git status at recovery time unless that read is itself a recorded step.

**A3. Idempotency keys on run start, on signals, and on external effects**
- *Who:* Restate: the `idempotency-key` header dedupes invocations, results are retained 24 h, and you can *attach* to a running invocation ([invocations](https://docs.restate.dev/foundations/invocations)). Trigger.dev v4: "All trigger and wait operations now support idempotency keys", and a subtask output is cached against the key so parent retries get the cached result ([v4 GA](https://trigger.dev/launchweek/2/trigger-v4-ga), [wait for token](https://trigger.dev/docs/wait-for-token)). DBOS queues deduplicate ([DBOS TS](https://github.com/dbos-inc/dbos-transact-ts)). Cloudflare: "Instance IDs Must Be Unique" ([rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)). Restate sagas thread a deterministic per-step key into downstream idempotency headers ([sagas](https://docs.restate.dev/guides/sagas)).
- *Why:* Exactly-once *effects* are impossible in general. What you can get is at-least-once execution plus idempotent effects, which behaves as effectively-once.
- *For GeneratorAI:* Webhook, cron and UI "Run" triggers need a client-supplied idempotency key, because double-clicking Run should not start two runs. Approval responses should be idempotent too: approving twice resolves once.

**A4. Make steps granular; keep payloads small; pass references**
- *Who:* Cloudflare: "Make Steps Granular", "Keep Step Returns Under 1 MiB … return references" ([rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)). Temporal: use references to stay under the 2 MB payload limit ([saga guidance](https://docs.temporal.io/design-patterns/saga-pattern)) and the event-history limits ([limits](https://docs.temporal.io/workflow-execution/limits)).
- *For GeneratorAI:* Store full transcripts and diffs as artifacts (files or blob rows). The stage *result* row should hold only a structured summary plus artifact references.

**A5. Durability modes (latency vs safety knob)**
- *Who:* LangGraph `durability="exit" | "async" | "sync"`. The default is async, which carries "a small risk" of losing a checkpoint on crash. It also persists per-task pending writes so successful sibling nodes are not re-run ([durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)).
- *For GeneratorAI:* Stage completion must be written synchronously. Streaming deltas can be async or lossy because they are observability, not state.

**A6. Leases and heartbeats for liveness**
- *Who:* Temporal heartbeat timeout; on retry the activity can read its last heartbeat details ([detecting activity failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures)). Step Functions: `HeartbeatSeconds` plus `SendTaskHeartbeat`, and the docs recommend heartbeats on every callback task ([best practices](https://docs.aws.amazon.com/step-functions/latest/dg/sfn-best-practices.html)). DBOS detects PENDING workflows at startup in single-node mode ([architecture](https://docs.dbos.dev/architecture)).
- *For GeneratorAI:* The lease should be renewed by the *agent stream* itself (any token or tool event counts as a heartbeat). A stage can then separate "hung" (no events for N seconds) from "slow" (long but active). This is the Temporal heartbeat vs start-to-close distinction.

### B. Versioning and in-flight run pinning

**B1. Pin a run to the definition/code version it started on**
- *Who:* Airflow 3: "A DAG will run through to completion based on the version at start", and runs show the version they ran with ([3.0 release notes](https://airflow.apache.org/docs/apache-airflow/3.0.0/release_notes.html), [GA blog](https://airflow.apache.org/blog/airflow-three-point-oh-is-here/)). Trigger.dev: runs are locked at start, retries use the original version, and child runs are locked to the parent's version ([versioning](https://trigger.dev/docs/versioning)). Vercel WDK: "every workflow run is pinned to the code version that created it" ([Vercel Workflows](https://vercel.com/docs/workflows)). Temporal Pinned workflows "don't need to be patched" ([Worker Versioning](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning)). DBOS tags each workflow with an app version (hash of the source) and recovers only matching versions ([DBOS FAQ](https://docs.dbos.dev/faq), [upgrading](https://docs.dbos.dev/java/tutorials/upgrading-workflows)).
- *Why:* Editing a workflow mid-run is the most common source of "impossible" states in DAG editors.
- *For GeneratorAI:* Snapshot `{dag, stage configs, prompt text, skill versions, MCP server config, model}` into the run at start, and render run views from that snapshot. The Sept 2026 audit found stage-param drift on first save and template-fidelity issues, which is the same class of bug.

**B2. Explicit migration of in-flight runs (patching / fork-to-new-version)**
- *Who:* Temporal `patched()` / `deprecatePatch()` for auto-upgrade workflows ([TS versioning](https://docs.temporal.io/develop/typescript/workflows/versioning)). DBOS lets you fork to a different code version programmatically ([forks blog](https://www.dbos.dev/blog/handling-failures-workflow-forks)). Restate resumes paused invocations on a *different deployment* ([1.5](https://restate.dev/blog/announcing-restate-1-5)). Inngest: an unchanged step ID keeps the memoized result, and a changed ID re-runs the step ([Inngest versioning](https://www.inngest.com/docs/learn/versioning)).
- *For GeneratorAI:* Provide "Fork this run onto the latest definition from stage X". Completed stages stay memoized where the stage ID and config hash match, and re-run where they don't. This gives Inngest's ID-based semantics with a config hash.

**B3. Rainbow deployments for long-running agents**
- *Who:* Anthropic: "rainbow deployments to avoid disrupting running agents" ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)). Temporal rainbow deployments with ramping ([Worker Versioning](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning)).
- *For GeneratorAI (desktop/self-host):* On app upgrade, drain or pause in-flight runs, or resume them under the pinned snapshot. Never silently continue them with new server semantics.

### C. Retries and error classification

**C1. Exponential backoff + jitter + max delay**
- *Who:* Step Functions `BackoffRate`, `JitterStrategy: FULL`, `MaxDelaySeconds` ([error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)). Prefect `exponential_backoff` + `retry_jitter_factor` ([retries](https://docs.prefect.io/v3/how-to-guides/workflows/retries)). Argo `backoff.duration/factor/cap/maxDuration` ([retries](https://argo-workflows.readthedocs.io/en/latest/retries/)). Cloudflare defaults to 5 retries, 10 s delay, exponential, 10 min timeout ([sleeping and retrying](https://developers.cloudflare.com/workflows/build/sleeping-and-retrying)). Serverless Workflow: constant/linear/exponential backoff, jitter, and limits by count or duration ([DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)).

**C2. Non-retryable errors and server-directed retry delay**
- *Who:* Temporal `non_retryable_error_types`, or marking an error non-retryable at throw site ([timeouts and retries](https://docs.temporal.io/evaluate/features/timeouts-and-retries)). Inngest `NonRetriableError` and `RetryAfterError` ([errors](https://www.inngest.com/docs/features/inngest-functions/error-retries/inngest-errors)). Vercel WDK `FatalError` vs `RetryableError` ([FatalError](https://www.mintlify.com/vercel/workflow/api-reference/workflow/fatal-error) [3p mirror]). Prefect `retry_condition_fn` ([retries](https://docs.prefect.io/v3/how-to-guides/workflows/retries)). Argo `retryStrategy.expression` over `lastRetry.exitCode/status/duration` ([retries](https://argo-workflows.readthedocs.io/en/latest/retries/)). Step Functions `ErrorEquals`, with `States.ALL` last ([error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)).
- *Why for LLMs:* Retry 429/529/5xx and transport errors (honour `Retry-After`). Do **not** blindly retry max-turns, budget-exceeded, permission-denied or validation failures. Validation failures should go to a *repair* loop (see H2), not a plain retry.

**C3. Retry vs error-routing interaction**
- *Who:* In n8n, if "Retry On Fail" is enabled *and* On Error is "Continue", retries are silently skipped ([n8n#10763](https://github.com/n8n-io/n8n/issues/10763)). n8n's model is: Stop (triggers the error workflow), Continue, or Continue using an error output branch ([error handling](https://docs.n8n.io/flow-logic/error-handling/)).
- *For GeneratorAI:* Define the ordering precisely: retries are exhausted *first*, then `on_failure` edges fire. The Sept 2026 audit found skip-then-validate retry ordering and a no-op run-retry, which is the same class of bug.

**C4. Pause instead of fail on exhausted retries**
- *Who:* Restate 1.5: invocations "automatically pause when retries are exhausted", preserving the journal ([1.5](https://restate.dev/blog/announcing-restate-1-5)). Step Functions redrive within 14 days ([redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html)). Inngest bulk Replay "death of the dead letter queue" ([replay](https://www.inngest.com/docs/platform/replay)).

### D. Timeouts

**D1. Separate queue wait, attempt, total and heartbeat timeouts**
- *Who:* Temporal defines four activity timeouts. Schedule-to-Start (queue wait, never retried), Start-to-Close (one attempt), Schedule-to-Close (all attempts) and Heartbeat ([activity timeouts blog](https://temporal.io/blog/activity-timeouts), [detecting failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures)). Step Functions uses `TimeoutSeconds` + `HeartbeatSeconds` ([stuck executions](https://docs.aws.amazon.com/step-functions/latest/dg/sfn-stuck-execution.html)). Cloudflare: cap step timeouts at about 30 min and use `waitForEvent` for longer waits ([rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)). Serverless Workflow timeouts use `after` durations ([DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)).
- *For GeneratorAI:* A single "stage timeout" conflates these. Suggested split: `queueTimeout` (waiting for a concurrency slot), `attemptTimeout`, `totalTimeout` (including retries) and `idleTimeout` (no stream events). Time spent in an approval wait must not count toward any of them.

### E. Control flow

**E1. Conditionals on outcomes, beyond success/failure**
- *Who:* Argo "enhanced depends": `task.Succeeded`, `.Failed`, `.Skipped`, `.Omitted`, `.Daemoned`, `.AnySucceeded`, `.AllFailed`, and boolean `&& || ()` ([enhanced depends](https://argo-workflows.readthedocs.io/en/latest/enhanced-depends-logic/)). Step Functions Choice rules ([Choice](https://docs.aws.amazon.com/step-functions/latest/dg/state-choice.html)). CrewAI `@router`, `or_`, `and_` ([Flows](https://docs.crewai.com/en/concepts/flows)). MS Agent Framework switch-case and conditional edges ([edges](https://learn.microsoft.com/en-us/agent-framework/workflows/edges)). Serverless Workflow `switch` ([DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)).
- *For GeneratorAI:* Add a distinct **Skipped** outcome and define its propagation. Argo's default treats unspecified dependencies as `Succeeded || Skipped || Daemoned`. Allow routing on *structured output fields* (e.g. `review.verdict == "reject"`), not only on status.

**E2. Loops with hard caps (evaluator-optimizer)**
- *Who:* Mastra `.dowhile`/`.dountil` ([control flow](https://mastra.ai/docs/workflows/control-flow)). Google ADK `LoopAgent`, which stops on `max_iterations` or when a sub-agent emits `escalate=True` ([loop agents](https://google.github.io/adk-docs/agents/workflow-agents/loop-agents/)). Serverless Workflow `for` with `while` ([DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)). Anthropic: evaluator-optimizer is effective "when [there are] clear evaluation criteria", with stopping conditions such as a maximum number of iterations ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)).
- *For GeneratorAI:* A DAG cannot express loops. Model a *loop block* (a subgraph with `maxIterations`, an exit condition and a per-iteration memo key) rather than allowing cycles.

**E3. Map / foreach fan-out with concurrency caps and failure tolerance**
- *Who:* Step Functions Distributed Map with `MaxConcurrency` and `ToleratedFailurePercentage` (default 0), plus Map Run redrive ([distributed map](https://docs.aws.amazon.com/step-functions/latest/dg/state-map-distributed.html), [redrive map run](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-map-run.html)). Mastra `.foreach(step, {concurrency})` ([control flow](https://mastra.ai/docs/workflows/control-flow)). LangGraph `Send` for map-reduce ([graph API](https://docs.langchain.com/oss/python/langgraph/use-graph-api)). Argo `withItems` with `AnySucceeded`/`AllFailed` ([enhanced depends](https://argo-workflows.readthedocs.io/en/latest/enhanced-depends-logic/)). DBOS durable queues ([DBOS TS](https://github.com/dbos-inc/dbos-transact-ts)).
- *For GeneratorAI:* A "fan-out stage" takes a list output from an upstream stage and runs N agent sessions with a cap, a tolerated-failure %, a per-item memo key and per-item redrive. Anthropic's research system scales effort rules inside the prompt (few subagents for simple queries, many for complex ones) ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)).

**E4. Joins: AND, OR (discriminator), N-of-M, and cancellation of losers**
- *Who:* van der Aalst patterns. The *Discriminator* fires once when the first incoming branch completes; the *N-out-of-M join* waits for N ([workflowpatterns.com control patterns](http://www.workflowpatterns.com/patterns/control/), [Wikipedia](https://en.wikipedia.org/wiki/Workflow_pattern)). Serverless Workflow `fork.compete: true`: "branches race each other; only the winning branch's output becomes the task result" ([DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)). BPMN Complex Gateway with `activationCondition` ([Camunda BPMN reference](https://camunda.com/bpmn/reference/)). Step Functions Parallel waits for all branches ([Parallel](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html)).
- *Why for LLMs:* *Voting* (Anthropic's parallelization pattern ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents))) needs N-of-M. *Racing* multiple models or approaches needs discriminator plus cancellation.
- *For GeneratorAI:* Add a join policy per node (`all` / `any` / `n_of_m` / `quorum`) and `cancelRemaining: boolean`. Today's `on_completion` / `always` semantics don't say what happens when two parents disagree.

**E5. Deferred choice (event-based gateway) and wait-any**
- *Who:* Deferred choice delays the branch decision until an external event occurs ([workflow patterns](https://en.wikipedia.org/wiki/Workflow_pattern)). BPMN event-based gateway ([Camunda](https://camunda.com/bpmn/reference/)). Serverless Workflow `listen` with `all` / `any` / `one` / `until` ([DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)). Hatchet or-groups combine sleep and event conditions ([conditions](https://docs.hatchet.run/v1/conditions)).
- *For GeneratorAI:* An approval gate *is* a deferred choice: approve, reject, or timeout. Timeout should be a first-class outgoing edge.

**E6. Cancellation regions / cancel-if**
- *Who:* Cancel Region, WCP25 ([Wikipedia](https://en.wikipedia.org/wiki/Workflow_pattern)). Hatchet `cancel_if` and `skip_if` on events ([conditions](https://docs.hatchet.run/v1/conditions)). Inngest `cancelOn` ([errors/retries](https://www.inngest.com/docs/functions/retries)). Hatchet `CANCEL_IN_PROGRESS` ([concurrency](https://docs.hatchet.run/v1/concurrency)).
- *For GeneratorAI:* Stopping a run must cancel all in-flight agent sessions in a group and emit a terminal state per stage. The Sept 2026 chat audit found a "Stop-while-pending stuck" bug, which is the same class.

**E7. Sub-workflows with isolated history**
- *Who:* Temporal child workflows have their own histories; a parent should not spawn more than about 1,000 children. Continue-as-new resets history ([child workflows](https://docs.temporal.io/child-workflows), [continue-as-new](https://docs.temporal.io/workflow-execution/continue-as-new)). Mastra nested workflows, including time travel into them via dot notation ([time travel](https://mastra.ai/docs/workflows/time-travel)). LangGraph subgraphs ([graph API](https://docs.langchain.com/oss/python/langgraph/use-graph-api)). Trigger.dev children are version-locked to the parent ([versioning](https://trigger.dev/docs/versioning)).

**E8. Dynamic DAGs (orchestrator-workers)**
- *Who:* Anthropic orchestrator-workers: "a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results" ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Inngest AgentKit Networks are "while loops with memory (State)", with a code-based or LLM Router ([networks](https://agentkit.inngest.com/concepts/networks), [routers](https://agentkit.inngest.com/concepts/routers)). AgentKit deterministic state routing ([routing](https://agentkit.inngest.com/advanced-patterns/routing)). MS Agent Framework magentic/handoff orchestrations ([samples](https://github.com/microsoft/Agent-Framework-Samples/tree/main/07.Workflow)). OpenAI Agents SDK handoffs transfer control ([guardrails/tracing docs](https://openai.github.io/openai-agents-python/tracing/)).
- *For GeneratorAI's orchestrator mode:* Record each orchestrator decision ("spawn worker W with brief B") as a durable step *before* executing it. That way recovery replays the decision and does not re-ask the LLM, which is the Temporal/Restate rule of journaling non-deterministic results. Prefer a **typed router** (AgentKit's typed state plus deterministic routing) for anything that can be coded, and reserve LLM routing for open-ended tasks.

### F. Human-in-the-loop

**F1. Durable wait-for-event with correlation + timeout that frees the worker**
- *Who:* Inngest `step.waitForEvent({event, match|if, timeout})` returns the event or `null` on timeout ([ref](https://www.inngest.com/docs/reference/typescript/functions/step-wait-for-event), [HITL pattern](https://www.inngest.com/docs/ai-patterns/human-in-the-loop)). Trigger.dev waitpoint tokens pause the run (no charge while waiting), return a callback URL, and support an idempotency key ([wait for token](https://trigger.dev/docs/wait-for-token), [waitpoints](https://trigger.dev/changelog/waitpoints)). Step Functions `.waitForTaskToken` ([integration patterns](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)). Airflow 3.1 HITL, Approval, Branch and Entry operators are *deferrable* and release the worker slot ([HITL operators](https://airflow.apache.org/docs/apache-airflow-providers-standard/stable/operators/hitl.html)). Cloudflare: waiting instances do not count toward concurrency ([CF Workflows](https://developers.cloudflare.com/workflows/)). Vercel WDK `createHook` / `createWebhook` ([3p summary](https://mcpservers.org/agent-skills/vercel/workflow/workflow)).
- *For GeneratorAI:* An approval should (a) release the concurrency slot, (b) survive restart, (c) carry a typed form schema (Airflow `HITLEntryOperator`), (d) have a timeout with a default outcome edge, and (e) accept responses from web, mobile or TUI via a token.

**F2. Typed signals vs validated synchronous updates vs read-only queries**
- *Who:* Temporal Signals are async and fire-and-forget. Updates are synchronous and tracked, can return values, and have an optional *validator* that can reject. Queries are read-only ([message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing), [handling messages](https://docs.temporal.io/handling-messages)). MS Agent Framework: pending RequestInfo events are saved in checkpoints and re-emitted on restore ([HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)).
- *For GeneratorAI:* "Approve with edits" is an *Update*: validate the edit, reject it if the stage is no longer waiting, and return the new state. Mid-run steering ("tell the orchestrator to also check X") is a *Signal* and should be journaled.

**F3. HITL on individual tool calls, not just between stages**
- *Who:* n8n gates selected AI-agent tools behind human review ([HITL for tools](https://docs.n8n.io/advanced-ai/human-in-the-loop-tools/)). LangGraph `interrupt()` inside nodes. Important caveat: on resume "the runtime restarts the entire node from the beginning", so side effects before `interrupt()` must be idempotent, and `interrupt` must not be wrapped in a bare try/except ([interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)).
- *For GeneratorAI:* Harness permission prompts (Claude Agent SDK `canUseTool`) should be persisted as durable approval records. A restart would otherwise lose them.

### G. Compensation / sagas

- *Who:* Temporal saga pattern: push compensations and unwind LIFO. Compensations need generous retries ([saga](https://docs.temporal.io/design-patterns/saga-pattern)). Restate sagas in plain code with idempotent compensations ([sagas](https://docs.restate.dev/guides/sagas)). Prefect 3 transactions with an `on_rollback` hook; rollback fires when the enclosing transaction fails ([transactions](https://docs.prefect.io/v3/advanced/transactions)). BPMN compensation boundary events ([Camunda](https://camunda.com/bpmn/reference/)). Argo `onExit` "always executes, irrespective of success or failure" ([exit handlers](https://argo-workflows.readthedocs.io/en/latest/walk-through/exit-handlers/)). Step Functions `Catch` routes to compensating states ([error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)).
- *Why for coding agents:* Stages mutate worktrees, branches, PRs and tickets. For worktree/git effects, the natural compensation is *checkpoint → restore*.
- *For GeneratorAI:* Per-stage `compensate` hook plus a workflow-level `finally`/exit hook. Record git checkpoints as effects so rollback is possible.

### H. LLM-specific practices

**H1. Typed inputs/outputs between nodes and schema-validated step output**
- *Who:* Mastra `createStep({inputSchema, outputSchema})` using Standard JSON Schema (Zod, Valibot, ArkType) ([Step](https://mastra.ai/reference/workflows/step), [overview](https://mastra.ai/docs/workflows/overview)). OpenAI Agents SDK `output_type`: the loop ends when the output matches the type ([running agents](https://openai.github.io/openai-agents-python/running_agents/)). Dagster *blocking* asset checks stop downstream materialization ([asset checks](https://docs.dagster.io/guides/test/asset-checks)). Anthropic prompt chaining adds "programmatic gates" between steps ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)).
- *For GeneratorAI:* Each stage declares an `outputSchema`, and the harness is asked for structured output (the final tool call or a JSON block). Validation failure triggers a **repair turn** in the *same session* ("your output failed schema X: …") before counting as a retry. Downstream prompt templating binds to typed fields, not to raw transcript text.

**H2. Evaluator-optimizer loops and step-level evals**
- *Who:* Anthropic evaluator-optimizer ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Mastra scorers attached to workflow steps with a sampling rate, with results stored in `mastra_scorers` ([evals](https://mastra.ai/docs/evals/overview), [createScorer](https://mastra.ai/reference/evals/create-scorer)). Anthropic uses LLM-as-judge for research-output evaluation ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)). Google ADK LoopAgent for iterative refinement ([loop agents](https://google.github.io/adk-docs/agents/workflow-agents/loop-agents/)).
- *For GeneratorAI:* Validation rules should come in two tiers. **Hard** rules (schema, regex, tests pass, file exists) gate the stage. **Soft** rules (LLM-judge score ≥ threshold) can drive a bounded evaluator-optimizer loop. Persist scores for regression tracking across workflow versions.

**H3. Guardrails: blocking vs parallel, tripwire semantics**
- *Who:* OpenAI Agents SDK input/output guardrails return `tripwire_triggered`, which raises and stops the run. Guardrails run *in parallel* by default (best latency, but the agent may already have spent tokens and run tools) or *blocking* (`run_in_parallel=False`) ([guardrails](https://openai.github.io/openai-agents-python/guardrails/)).
- *For GeneratorAI:* Pre-stage guardrails such as secret or PII scans of the prompt and policy checks on the target repo should be *blocking*. Output guardrails run before `on_success` edges fire.

**H4. Budget limits: turns, tokens, dollars, wall-clock**
- *Who:* Claude Agent SDK `maxTurns` (result subtype `error_max_turns`) and `maxBudgetUsd` (`error_max_budget_usd`) ([agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [TS reference](https://platform.claude.com/docs/en/agent-sdk/typescript)). OpenAI Agents SDK `max_turns` → `MaxTurnsExceeded` ([running agents](https://openai.github.io/openai-agents-python/running_agents/)). Anthropic: agents use about 4× and multi-agent systems about 15× the tokens of chat ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)).
- *For GeneratorAI:* Budgets should be hierarchical: per stage (passed to the harness), per run (the engine sums stage costs and refuses new stages or pauses for approval when exceeded) and per orchestrator (caps worker spawns). Budget exhaustion is a non-retryable error that routes to `on_failure` or to an approval gate ("continue with +$5?").

**H5. Model fallback chains**
- *Who:* Mastra agents accept a fallback array of `{model, maxRetries}`. Retryable errors (5xx, 429, timeout) exhaust retries and then move to the next model. Non-retryable 4xx do not trigger fallback ([model fallbacks blog](https://mastra.ai/blog/model-fallback), [changelog](https://mastra.ai/blog/changelog-2026-03-16)).
- *For GeneratorAI:* Multi-harness is a natural fallback axis (Claude → Copilot → Codex). Record which model or harness actually ran in the stage result, for cost accounting and for replay fidelity.

**H6. Caching of step results (work avoidance)**
- *Who:* Prefect cache policies `DEFAULT` (inputs + code + run), `INPUTS` and `TASK_SOURCE` ([task caching](https://docs-3.prefect.io/v3/develop/task-caching)). LangGraph node `CachePolicy(key_func, ttl)` ([CachePolicy](https://reference.langchain.com/python/langgraph/types/CachePolicy)). Argo memoization with `key` + `maxAge` in a ConfigMap cache ([memoization](https://argo-workflows.readthedocs.io/en/latest/memoization/)). Trigger.dev idempotency-key cached subtask outputs ([v4](https://trigger.dev/launchweek/2/trigger-v4-ga)). Inngest "Don't pay for the same step twice" ([blog](https://www.inngest.com/blog/dont-pay-for-the-same-step-twice)).
- *For GeneratorAI:* An opt-in stage cache keyed by `hash(resolved prompt, stage config, model, input artifacts' content hashes, repo HEAD)`, with a TTL. It is especially valuable while *authoring* workflows. Default it off for stages with external side effects.

**H7. Context engineering between steps: artifacts vs full transcript**
- *Who:* Anthropic: subagents "explor[e] … with their own context windows … before condensing the most important tokens", and direct subagent outputs to a filesystem bypass the coordinator to avoid information loss ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)). Compaction, structured note-taking and sub-agent architectures ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). AgentKit State combines message history with a *typed* KV store ([state](https://agentkit.inngest.com/concepts/state)). Step Functions variables let later states reference earlier results without threading payloads ([variables](https://docs.aws.amazon.com/step-functions/latest/dg/workflow-variables.html)).
- *For GeneratorAI:* The default inter-stage contract should be **structured output + named artifacts**, with an explicit per-edge choice of `summary | artifacts | full transcript`. Passing the full transcript by default burns context and degrades downstream stages.

**H8. AI-call observability and edit-and-rerun**
- *Who:* Inngest `step.ai.infer` / `step.ai.wrap` provide request/response tracking, usage stats, and "the ability to edit inputs from the middle of a workflow and rerun" ([step.ai](https://www.inngest.com/docs/features/inngest-functions/steps-workflows/step-ai-orchestration), [blog](https://www.inngest.com/blog/ai-orchestration-with-agentkit-step-ai)).

### I. Concurrency, rate limiting, priority, queues

- *Who:* Inngest concurrency limits executing steps per key; throttling limits run *starts*; plus rate limit, debounce, singleton and priority `run` expression within ±600 s ([flow control](https://www.inngest.com/docs/guides/flow-control), [concurrency](https://www.inngest.com/docs/guides/concurrency), [throttling](https://www.inngest.com/docs/guides/throttling), [priority](https://www.inngest.com/docs/guides/priority), [singleton](https://www.inngest.com/docs/guides/singleton)). Hatchet `GROUP_ROUND_ROBIN` fairness and `CANCEL_IN_PROGRESS`, plus static/dynamic rate limits ([concurrency](https://docs.hatchet.run/v1/concurrency)). Temporal priority 1–5 plus fairness keys (GA) ([priority/fairness](https://docs.temporal.io/develop/task-queue-priority-fairness), [GA](https://temporal.io/changelog/priority-fairness-generally-available)). DBOS queues offer per-queue and per-process concurrency, rate limits, dedup and priority ([DBOS TS](https://github.com/dbos-inc/dbos-transact-ts)); DBOS Java adds runtime-mutable queues and debouncing ([June 2026](https://www.dbos.dev/blog/new-in-dbos-june-2026)). Trigger.dev queues with per-key and total concurrency ([concurrency and queues](https://trigger.dev/product/concurrency-and-queues)).
- *For GeneratorAI:* The keys that matter locally are `provider/model` (API rate limits), `harness` (process and memory cost of each SDK subprocess), `repo/worktree` (a singleton writer per worktree prevents two agents clobbering one checkout) and `global` (machine capacity). Add debounce for file-watch or webhook triggers.

### J. Observability

**J1. OTel GenAI semantic conventions**
- *Who:* Spans `invoke_agent {gen_ai.agent.name}` → `chat` (model call, with `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`, `gen_ai.response.finish_reasons`) → `execute_tool`. Metrics `gen_ai.client.token.usage` and `gen_ai.client.operation.duration`. Prompt and tool-argument content capture is **opt-in**. The conventions are still under active development and now live in their own repo ([OTel GenAI blog 2026](https://opentelemetry.io/blog/2026/genai-observability/), [agent spans spec](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)). OpenAI Agents SDK traces every generation, tool call, handoff and guardrail by default ([tracing](https://openai.github.io/openai-agents-python/tracing/)). Inngest step traces are exposed as OTel spans ([traces](https://www.inngest.com/docs/platform/monitor/traces)).
- *For GeneratorAI:* Map run → workflow span, stage → `invoke_agent`, and harness turns → `chat` / `execute_tool`. Per-stage cost and token rollups then fall out of standard attributes and can be exported to any OTel backend while staying local by default.

**J2. Live execution timeline + rerun-from-node + run history**
- *Who:* Restate 1.5 has a live timeline of steps, retries and nested calls, plus "Restart as new" ([1.5](https://restate.dev/blog/announcing-restate-1-5)). Hatchet DAG timeline in its dashboard ([GitHub](https://github.com/hatchet-dev/hatchet)). Inngest single-step rerun with edited input, plus bulk Replay ([rerun](https://www.inngest.com/docs/platform/manage/rerun-function-runs), [replay](https://www.inngest.com/docs/platform/replay)). DBOS fork from step N copies earlier step outputs ([forks](https://www.dbos.dev/blog/handling-failures-workflow-forks)). Mastra `timeTravel()` / `timeTravelStream()` ([time travel](https://mastra.ai/docs/workflows/time-travel)). LangGraph replay and fork: "Nodes before the checkpoint are not re-executed" ([time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)). Step Functions redrive ([redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html)). Temporal reset to an event ID, with signal reapply options ([CLI workflow](https://docs.temporal.io/cli/workflow)). Trigger.dev Realtime React hooks and streams ([realtime hooks](https://trigger.dev/docs/frontend/react-hooks/realtime), [streams](https://trigger.dev/docs/realtime/react-hooks/streams)). Airflow 3 shows the DAG version per run ([GA blog](https://airflow.apache.org/blog/airflow-three-point-oh-is-here/)).
- **Run diffing** (comparing two runs' stage outputs, prompts or costs side by side) was **not found as a first-class feature** in the orchestration engines surveyed. It lives in eval tooling instead. This is an opportunity for GeneratorAI: diff a forked run against its parent.

### K. Testing

- **Test single node / pinned data:** n8n "Execute step" runs a node plus the upstream nodes it needs. Pinned output data replaces a node's execution in manual runs (production ignores pins). "Copy to editor" pins a past execution's data ([partial executions](https://docs.n8n.io/workflows/executions/manual-partial-and-production-executions/), [data pinning](https://docs.n8n.io/data/data-pinning/), [debug](https://docs.n8n.io/workflows/executions/debug/)). Mastra time travel with custom context "testing individual steps with different inputs" ([time travel](https://mastra.ai/docs/workflows/time-travel)).
- **Deterministic replay tests:** Temporal `Worker.runReplayHistory` throws `DeterminismViolationError` when new code is incompatible with recorded histories ([TS testing](https://docs.temporal.io/dev-guide/typescript/testing)).
- **Evals for LLM steps:** Mastra per-step scorers with sampling ([evals](https://mastra.ai/docs/evals/overview)). Anthropic: start evals small and early, use LLM-as-judge, and keep humans in the loop ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)).
- *For GeneratorAI:* (1) "Run this stage only" using pinned upstream outputs taken from a past run, (2) a replay test that runs the scheduler over recorded stage results and asserts the same edge decisions, which catches AND/OR evaluation regressions, and (3) a per-stage eval dataset built from pinned inputs.

### L. Triggers, scheduling and secrets

- **Cron / events / webhooks:** DBOS cron scheduling plus durable sleep for days or weeks ([DBOS TS](https://github.com/dbos-inc/dbos-transact-ts)). Airflow asset-aware scheduling, with partition-granular triggers from 3.2 ([asset scheduling](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/asset-scheduling.html), [3.2 blog](https://airflow.apache.org/blog/airflow-3.2.0/)). Dagster declarative automation, e.g. `on_cron(...) & any_deps_updated()` ([declarative automation](https://docs.dagster.io/guides/automate/declarative-automation)). Vercel WDK `createWebhook` ([3p summary](https://mcpservers.org/agent-skills/vercel/workflow/workflow)). Inngest debounce and batching for bursty events ([flow control](https://www.inngest.com/docs/guides/flow-control)).
- **Asset / data-aware triggers** are relevant to GeneratorAI. Examples: "run the review workflow when branch X changes" or "when the spec doc is updated". This is Dagster/Airflow-style asset scheduling applied to repos and documents.
- **Secrets:** Do not persist secret values in step results or traces. OTel GenAI content capture is opt-in precisely because prompts and tool args can hold sensitive data ([OTel blog](https://opentelemetry.io/blog/2026/genai-observability/)). Pass secret *references* in definitions and resolve them at stage start. GeneratorAI already has an encrypted vault (per project memory), so the rule is to redact before journaling.

## 4. Control-flow pattern reference (formal)

| Pattern (van der Aalst WCP) | Meaning | Engine realisations | GeneratorAI need |
|---|---|---|---|
| Sequence / parallel split / synchronization | basic | all | have |
| Exclusive choice / simple merge | if/else | Step Functions Choice, Serverless `switch`, CrewAI `@router` | have (edge conditions) |
| Multi-choice / synchronizing merge | OR-split + OR-join | Argo enhanced depends | partial: needs Skipped semantics |
| **Discriminator** | first of N wins, fires once | Serverless `fork.compete` | racing models or approaches |
| **N-out-of-M join** | wait for N of M | BPMN complex gateway, Step Functions `ToleratedFailurePercentage` (inverse) | voting / quorum review |
| **Deferred choice** | branch chosen by an external event | BPMN event-based gateway, Serverless `listen any`, Hatchet or-groups | approve / reject / timeout |
| **Cancel region** | cancel a set of activities | Hatchet `cancel_if`, Inngest `cancelOn` | stop run, cancel losers |
| **Multi-instance without a priori knowledge** | fan-out count known only at runtime | Distributed Map, LangGraph `Send`, Mastra `.foreach` | fan-out over orchestrator-produced lists |
| Structured loop | while / until | Mastra `.dowhile`, ADK LoopAgent, Serverless `for.while` | evaluator-optimizer |

Sources: [workflowpatterns.com](http://www.workflowpatterns.com/patterns/control/), [Wikipedia: Workflow pattern](https://en.wikipedia.org/wiki/Workflow_pattern), [YAWL report](http://www.workflowpatterns.com/documentation/documents/yawl_qut_report_FIT-TR-2002-06.pdf), [Serverless Workflow DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md), [Camunda BPMN reference](https://camunda.com/bpmn/reference/). The Serverless Workflow DSL 1.0 defines 12 tasks: `call`, `do`, `fork`, `emit`, `for`, `listen`, `raise`, `run`, `switch`, `set`, `try`, `wait` ([DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)). It is a good checklist for a stage-type palette.

**SQLite-specific design notes** (engineering inference from the above, not a single cited source):
- Keep one writer connection for engine state, in WAL mode. Claim work with `UPDATE … WHERE lease_expires_at < now RETURNING` inside a write transaction (Absurd's claim-based scheduling, adapted).
- Write the stage-result checkpoint in the *same transaction* as the edge-activation rows, so "stage done" and "next stages enqueued" are atomic. This matches the DBOS "one write per step" budget.
- Keep streaming deltas out of the durable tables, or in a separate append-only table with async durability (see A5).
- Back up with Litestream or the SQLite online backup API. Do not rely on atomic rename on OneDrive-synced paths (a known GeneratorAI env gotcha).
