## 1. Rules

### 1.1 Placement: `ui/` vs `blocks/` vs `features/`

| Question | Answer → location |
|---|---|
| Does it read a query, a store, the router or the platform? | No → `ui/` (kit document). Yes → continue. |
| Is it used by **two or more features** (chat, projects, agents, home, chats, settings, palette, workflow…), or is it named in this document as a block? | Yes → `apps/web/src/blocks/<block-name>/` with ID `B-xx`. |
| Used by one feature only? | `apps/web/src/features/<area>/components/` with ID `F-<area>-xx`. |
| A second feature starts needing a feature composite | Promote it to `blocks/` **in the PR that adds the second consumer** (move + re-export nothing; update imports). Never import across features (D-04 boundary: `features/*` MUST NOT import another feature; ESLint `boundaries/element-types` fails the build). |
| Workflow-only piece with no engine dependency (WF-xx) | `apps/web/src/blocks/workflow/` (the overhaul's screens and chat both consume them, so they are blocks by definition). |

Blocks may import `ui/`, `hooks/*Queries.ts`, `stores/`, `packages/client-core`, `packages/shared`. Blocks **must not** import `features/` or `app/`. A block folder contains: `Component.tsx` (the connected block), `Component.view.tsx` (the pure view, props-only, has stories), `useComponentData.ts` (the data hook, if non-trivial), `index.ts`, `*.stories.tsx`, `*.test.tsx`. The pure view is what Storybook renders (Storybook has no server), so **every block is split into a data hook + a pure view** even when small.

### 1.2 Data access

1. Components read server data **only** through hooks exported from `apps/web/src/hooks/*Queries.ts` (TanStack Query) or through zustand stores in `apps/web/src/stores/`, and **only via a view hook** (`useXxxView`) or a block data hook — never `platform.*`, `fetch`, `apiFetch`, `openMultiplexedStream` or `WebSocket` directly in a component body. Current violations that must move into hooks when their file is ported: `ChatPage.tsx` raw `fetch('/api/workspaces/:id/browser/{descriptor,start}')` and two `openMultiplexedStream` calls; `TerminalPanel.tsx` raw REST + WebSocket; `Security.tsx` `apiFetch` to 12 endpoints with its own 30 s polling; `CreateAutomationPage.tsx` `fetch('/api/automations/test-data-source')`; `ChatInput.tsx` `platform.getWorkspaceFileContent`; `ProjectDetailPage.tsx` DirectoryBrowser server calls.
2. New read models (attention feed, week stats, palette entity search, project columns, computer replay/grants, transcript view mode, model details) are added **in `packages/client-core`** first (D-36), exposed through a web `*Queries.ts` hook, then consumed. Until the endpoint exists, the element that needs it is **not rendered** — no placeholder data, no disabled mock (D-36). Every such element below is marked **GAP → 05-gap-matrix** with the needed shape.
3. Stream state (`useStreamStore`) is read with **narrow selectors** (one primitive or a memoised key per selector). The existing isolation pattern — only `LiveTranscript` subscribes to the whole stream (`ChatPage.tsx` 119–184) — is preserved by the transcript blocks.
4. Status → visual mapping goes through the shared 8-state map in `packages/shared` (D-18). A block receives a *server* status and calls `toVisualStatus(kind, serverStatus)`; it never keeps a local colour map. Local maps to delete are listed per block.

### 1.3 View hooks (when to write one)

A page or feature composite gets a dedicated view hook (`features/<area>/hooks/use<Name>View.ts`) **only if** (a) the current file is longer than ~400 lines, or (b) any event handler performs transport (mutations, SSE subscribe, IPC). The view hook returns `{ data, state, actions }` — plain values and stable callbacks — and the component body is JSX plus local UI state (open/closed, hover). Pages under ~400 lines with only query reads keep calling query hooks directly. Big files are decomposed per §6; each named hook there *is* the view hook split into concerns.

### 1.4 Testid and accessible-name preservation

1. Every `data-testid` and every accessible name (`aria-label`, visible button text used by `getByRole`) on a ported element **is kept verbatim**. The e2e suite has 56 testid selectors and 180 `getByRole` selectors; smokes (`agent-tests/desktop-chrome-smoke.mjs`, `right-pane-desktop-smoke.mjs`, `desktop-browser-smoke.mjs`) use `app-header`, `app-titlebar`, `right-pane*`, `header-toggle-*`.
2. Renaming a testid is allowed only when the element's *meaning* changes (e.g. `right-pane` → dock), and then the e2e/smoke update ships in the **same PR**. Renames planned by this document: `right-pane*` testids are **kept as aliases on the new DockFrame** until P7 (the dock is the same concept), `app-header` moves to `LegacyHeader` (D-21) and is deleted with it.
3. Testids listed per block/feature in this document are the ones to pin in characterization tests before splitting (§6).
4. New interactive elements get a testid only when an e2e test needs it; name them `<area>-<thing>` (e.g. `composer-send`, `dock-tab-changes`).

Four registries are introduced so later work (Workflow Overhaul P06, widgets, new tools) adds entries without reopening the host component. Each is a typed map in the owning block/feature, populated at module load by side-effect-free registration files in `app/registries/` (so features stay decoupled):
