## 3. Answers to the specific questions

### Q1 — `apps/mobile/src/theme/tokens.generated.ts`: old vs new, and does `check:tokens` cover it?

The file **is** produced by the current `emitNative()` in `packages/design-tokens/src/emit/native.ts` — running `tsx packages/design-tokens/bin/generate.ts --check` reports `ok mobile token module` (verified live), so **yes, `pnpm check:tokens` covers it** (it's target `"mobile token module"`, `optional: true` only so the generator doesn't fail before the app is scaffolded — the app exists, so it's fully checked).

The file (25,966 lines) contains **both** vocabularies side by side:
- The legacy/shadcn-shaped `themeVars` (`--background`, `--card`, `--popover`, `--sidebar-accent` …) — this is what `ThemeProvider.tsx` and `motion.ts` actually read today.
- The new M-01 names as `gaiColors` (`ground`, `surface`, `raised`, `overlay`, `sunken`, `hover`, `selected`, `line`/`line-soft`/`line-strong`, `fg`/`fg-2`/`fg-3`, `accent`, `on-accent`, `focus`, `run`/`run-bg`/`run-text`, `ok`/`ok-bg`/`ok-text`, `warn`/`warn-bg`/`warn-text`, `err`/`err-bg`/`err-text`, `add-bg`, `del-bg`, `scrim`) — generated, **but nothing in `apps/mobile` imports `gaiColors` yet**.

So: the resolver is already fully wired for mobile: nothing needs to be built on the token-generation side. What's outstanding is purely consumption — swapping NativeWind v4/Tailwind v3 for Uniwind/Tailwind v4 (M0) so `className="bg-surface"` etc. resolves against `--gai-*`, then deleting the legacy `themeVars` reads in `ThemeProvider.tsx`.

### Q5 — DOM/Node leakage in shared packages that would break Hermes/RN

The isolation is **already well engineered**, not ad hoc:
- `packages/shared/src/client.ts` is an explicit client-safe barrel ("the subset of shared that belongs on a phone or in a browser"), documented as excluding anything importing `node:*`, `pino`, `@opentelemetry/*`, `./config/AppConfig`, `./config/childEnv`, `./ipc/*`, `./telemetry/*`, `./logging/*`. Node-only pieces are isolated behind a separate `packages/shared/src/node.ts` (`readBuildStamp`, `makeHostHello` from `protocol/buildStamp.ts` which uses `node:fs`/`node:path`/`node:url`; `hashWebhookToken` from `security/webhookToken.ts` which uses `node:crypto`) — neither is re-exported from `client.ts`.
- The mobile Metro config aliases `@generatorai/shared` → `client.ts` at bundle time while `tsc` still checks against the full barrel; enforcement is a real test (`apps/mobile/src/__tests__/sharedClientEntry.test.ts`) plus `apps/mobile/scripts/check-bundle.mjs` (`bundle:check` in `apps/mobile/package.json`) that measured the Sept-2026 bundle-size regression this design fixes (≈420 KB shared source + `@opentelemetry/api` before the split).
- Grep across `packages/shared/src`, `packages/client-core/src`, `packages/client-runtime/src`, `packages/design-tokens/src` for `window.`/`document.`/`node:` imports/`Buffer`/`process.env|platform|cwd` found:
  - `packages/shared/src/types/IPlatformClient.ts:108` — `downloadArtifact(...)` return type includes a bare `Buffer` field. Type-only (erased at runtime) but needs `@types/node`-style global `Buffer` to type-check; worth confirming the mobile `tsconfig` has that or it'll need a `buffer` polyfill's types.
  - `packages/client-runtime/src/deviceKey.ts:60-63` — a guarded, safe Node `Buffer` fallback behind `typeof globalThis.Buffer` (does not break RN).
  - `packages/client-runtime/src/AuthenticatedClientRuntime.ts:190` — only a **comment** referencing `window.fetch` ("the web client wraps `window.fetch`..."), no runtime code; `setFetchImpl(impl: typeof fetch)` is transport-agnostic.
  - `packages/design-tokens/src/emit/prepaint.ts` uses `node:crypto`, and emits `document.`/`window.` **as string literals inside a generated browser script** — this file is Node-only build tooling (`bin/generate.ts`), never imported by mobile (mobile imports the generated `tokens.generated.ts` output, not the emitter source).
  - `packages/shared/src/config/{numericEnv,childEnv}.ts`, `logging/Logger.ts` default parameters to `process.env` — these are Node-only modules already excluded from `client.ts` per its own header, consistent with the isolation design.
  - No `window.`/`document.` hits at all in `packages/client-core/src`.

**Conclusion:** no actual DOM/Node leakage was found in the client-consumable surface; the one loose end is the `Buffer` type in `IPlatformClient.downloadArtifact`, which mobile should confirm compiles (or retype to `Uint8Array`/`ArrayBuffer` for a truly platform-neutral shape) before that method gets a mobile caller.
