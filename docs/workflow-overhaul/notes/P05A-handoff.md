## 1. The container machinery (what 5B builds on)

### Spec (`@generatorai/workflow-spec`)
- `StageSpecSchema` is a discriminated union `[agent, check, loop]` (`schemas/stage.ts`). A new kind is one more member spreading `stageBase`, one entry in `STAGE_KINDS`, `kindFields()` and (for a container) `CONTAINER_STAGE_KINDS`. `field-not-applicable` falls out of `kindFields()` automatically (`validate/validateWorkflow.ts` `notApplicable`). Remove `map`/`subworkflow`/`wait` from `FUTURE_KINDS` when they land.
- `stageTemplateFields(stage)` lists every template of a stage per kind (the validator type-checks them): add the map/wait/subworkflow templates there.
- Scopes and types: `validate/scope.ts` `GraphTypes`. `upstream(key)` = ancestors in the stage's own scope ∪ upstream of its container (never the container). `stagesRoot(visible, inside)` makes a body stage outside its scope `expr-scope-unavailable` and a not-yet-run one `expr-stage-not-upstream`. `outputType(key)` is per kind (a loop's output type includes its carry types, inferred by fixed point, and its `select` types). `env(place)` builds the environment of a place: `{kind: 'stage'|'edge'|'loop'|'workflow'|'pre'}`. For 5B: add `item`, `item.index`, `item.key`, `map.count`, `maps.<key>` in `loopRoots`-like fashion (`CONTAINER_ROOTS` currently reports them unavailable), and a map output type `{results: list<{index, key, item, status, stages: {...}, ...select}>, failures}`.
- Validator codes already there for any container: `nesting-too-deep` (≤ 3), `edge-crosses-scope`, `empty-body`, per-scope `cycle`, `parent-not-container`.
- `commandBearing.ts` registers `check` (kind `check`): `admin:settings` to add or edit one. `itemSetup` checks of a map are command-bearing too: register them.

### Engine (`packages/core/src/domain/scheduler/`)
- `working.ts`: the working copy (`Working`) — `ix()` (a `StateIndex` over the working state, rebuilt after every decision), `scopeInstances(containerId, iteration)`, `sibling(inst, key)` (same scope), `descendants(container)`, `ancestors(inst)`, `instancePatch` (columns without a status change; a CAS on the status in `RunStore`), `recordIteration`, `usage()` (rolls up into every enclosing container with `usage_rollup{scopeOnly}` so a container budget sees its body), and the building blocks (`stopInstance`, `cancelInstance` — which cascades into a container's body —, `failInstance`, `stageEvent`).
- `decide.ts` `settle()`: `resolveReadiness` runs in every **active scope** (`loops.ts activeScopes`: the top level + the current iteration of every running loop) to a fixed point together with `settleLoops`. A map adds its active item scopes to `activeScopes` (one per running item), and its own `settleMaps` to the fixed-point loop. Readiness finds predecessors with `w.sibling(inst, key)` (edges never cross a scope).
- `admit()` launches only `class === 'work'` nodes; containers start their scopes themselves (`ready → running`, `sched:scope_started`, `lease 'none'`). A `wait` is class `wait` (`ready → waiting`, no executor, no admission slot): give it its own branch in settle, like `settleLoops`.
- The run is `busy` when a work node is in an attempt/admitted or a loop has an effect in flight (`starting|settling|restoring`); extend that predicate for map merges and waits (a wait is NOT busy: the run is `waiting`).
- Scope outcome: `computeScopeOutcome(graph, scopeInstances, w.scopeFor)` works on any scope.
- Effects follow the loop's pattern: a decision (`capture_iteration`, `restore_iteration`) listed in `EFFECT_DECISIONS`, dispatched by `EffectsDispatcher` after the commit, answered by a message (`iteration_captured`, `iteration_restored`), re-dispatched by `RunSupervisor.recover()` from the persisted phase. Map's `forkFromSnapshot`/merge effects and the wait's callback token fit the same shape.
- Loop state lives in `stage_runs.loop_state` (`LoopState` in `types.ts`); a map should keep its own state object (P05 §4.1) in `stage_runs.loop_state` or `expansion` (both JSON; `expansion` is unused so far) via `InstancePatch`.

### Scopes and instance paths (the conventions)
- Top level: `instance_path = <key>`, `scopeId = null`, `iterationIndex = null`.
- Loop body: `<loopPath>#<k>/<bodyKey>`, `scopeId = <loop instance id>`, `iterationIndex = k`. Nested: `outer#1/inner#0/fix`.
- Loop wrap-up: `<loopPath>#wrapup/<stageKey>`, `scopeId = loop id`, `iterationIndex = null` (not part of any iteration scope; `isWrapUp()`).
- Map item (5B): `<mapPath>#<i>/<bodyKey>` with `itemIndex = i` (NewInstance already has `itemIndex` and `itemKey`; `create_instances` writes `stage_runs.item_key`, v59). `StateIndex.scope(containerId, iteration)` keys by `iterationIndex`: for a map, key the item scopes by `itemIndex` (extend `scopeKey` to use `iterationIndex ?? itemIndex`, or add a second index — a map instance never has both).
- Ids: `instanceId(runId, instancePath)` (UUIDv5), so replayed decisions create identical rows.
- Expression scopes (`scope.ts`): `instanceScope(ix, inst)` gives a body instance `stages` = top level + the same iteration of every enclosing loop, `loop` = the nearest loop in context T, `loops.<key>` = every enclosing loop. For a map body: `item`, `map.count`, `maps.<key>.item` from the chain (`ix.chain(inst)` returns each enclosing container with the iteration the instance belongs to).

### Executor (`services/engine/StageExecutor.ts`)
- `context()` finds the nearest enclosing loop (`ctx.loop = {inst, node, k}`), picks `followUpPrompts` from iteration 1, the wrap-up prompt for a wrap-up; `scopeOf(ctx)` = `templateScope(...)` (prompts, rules, hooks); context blocks come from the same scope.
- Session keys: `loop:<loopId>/<stageKey>#c<generation>` for a continuing body stage (and its wrap-up), else `instance:<path>@<epoch>`. A map item body stage with `sessionReuse: continue` has nothing to continue (fresh per item) unless the map is itself inside a loop — decide that with the map.
- Check stages run through `CheckRunner.ts` inside the executor's frame (`checkAttempt`); a map's `itemSetup` can call `runCheck` directly with the item mount as `primaryDir`.

### Admission
- `AdmissionController.admitFlow(flowKey, fn)`: flow keys separate from the lanes (`check:global` = 2 by default, `DEFAULT_FLOW_LIMITS`). The effects dispatcher picks the flow by the instance kind (`kindOf`). P07 surfaces the flow limits.

## 2. How the 5B kinds should plug in
- **map (WP-5B.1):** schema member + `CONTAINER_STAGE_KINDS`; `map.items` evaluated in the container's T scope at `ready`; item scopes created in batches of `concurrency` (the map's own settle); `toleratedFailurePercent` decides the map outcome over `computeScopeOutcome` per item; results built like `loopOutput` (per item `select` in the item's scope). `mount_per_item` needs `MountService.forkFromSnapshot` (all-or-nothing) as an effect before an item's scope exists, and the merge as an effect after it; hold `worktree:<mountId>` shared/exclusive leases (not implemented anywhere yet). `stage_runs.item_key` exists (v59).
- **subworkflow (WP-5B.2):** a container whose "scope" is a child run: invoke through `WorkflowInvocationService` with trigger `{kind:'stage'}` from an effect, persist the child run id (the child's `parent_stage_run_id` column exists since v57), and complete from the child's `workflow_run.finalized` (a message into the parent's actor). `WorkflowSpec.outputs` is validated (typed in the `workflow` place) but nothing computes it at run end yet: compute it from the child's final state when the subworkflow completes (the loop's `loopSettingsScope`/`evalExpr` show the pattern). Mirror parked loops into the parent's pending list: a parked loop is `awaiting_input` with `interruptData.kind === 'loop_decision'`.
- **wait (WP-5B.3):** class `wait` already has its STAGE_RUN_TRANSITIONS rows (`ready → waiting`, `waiting → completed|failed|cancelled`) and timer kinds (`wait_timeout`, `wait_timer` in `TimerKind`; `onTimer`'s default branch says so). `workflow_run_events` exists (v59; unique `(run_id, event_key, idempotency_key)`, pending index). `deliver_event` is a new `RunCommand` member.
- **Fork from `<loop>#k/…` (WP-5B.4):** `loop_iterations.carry` holds carry(k) for every finished iteration, so a fork re-running iteration k seeds the loop with `loop_state.carryInit = carry(k-1)` (or the row) and `k`. `forkRun` today copies memoized instances by path; it does not know loops yet.
- **Expression editor (WP-5B.5):** the scope model for autocomplete is `GraphTypes.env(place)` (every root with its type, `loop.*` included).

- **Tests:** none written beyond `migration59.test.ts` (IMPLEMENTATION FIRST). - **Budget signals on providers without usage:** the faux provider reports no usage, so budget exhaustion and the wrap-up were not exercised end to end.
- **`accept_best` / `accept_iteration` restore and the tree-hash signals** need `WorkspaceCheckpointService` (the server wires it late, `setCheckpoints`); neither the restore nor `workspaceChanged` was exercised against a real mount.
- **UI** was checked by typecheck, the existing tests and jsdom only (no browser, no device). The web run page subscribes to `loop.*` on its own (the client-core router does not route them); mobile reads loop fields through a local type; the TUI still injects a local `stage_run.input_received` after a decision although cli-core now clears the gate on `loop.command_applied`.

- **Loop decision commands** need `write:workflows` (only `approve` is `exec:agent`); a default paired phone sees the decision card but cannot act. Decide with the product owner whether loop decisions are run-time acts like `approve`.
- **Live E2E** (L1 on a fixture repo, L2 with a failing test): not run.
- **`describe_workflow`** (the P06 tool) should show the check stages' "runs repo code" risk: `planInvocation` already computes `risks`.
