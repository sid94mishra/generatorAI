GeneratorAI · internal architecture review

How GeneratorAI is built, how it authenticates, and how the browser relay actually connects things

A full walk-through of the monorepo, then two focused deep dives: the real end-to-end auth & credential story, and the browser CDP relay that lets an agent drive a live browser tab — including a direct answer to whether a "mobile" connection exists.

0What GeneratorAI is, in one paragraph

GeneratorAI is a self-hosted, single-tenant AI agent & workflow platform — think a personal, download-and-run n8n crossed with a coding-agent runtime. One Node/Express server holds all the logic; a React web app, an Electron desktop shell, and a terminal CLI are three different windows onto that same server. It runs multi-step "workflows" (DAGs of agent stages) and free-form "chats" on top of pluggable agent harnesses — today that's GitHub Copilot's SDK and Anthropic's Claude Agent SDK, each just a different engine bolted behind one common interface. It is built for one person/team running it on their own machine or VPS, not for many unrelated tenants sharing one deployment — that single fact explains almost every auth decision described below.

Alongside the main HTTP server it starts a second, tiny server on a different loopback port (default 3101) that serves only agent-rendered widget assets — a deliberate origin split so a widget's iframe HTML/JS can never read the main app's cookies or API key, the same idea browsers use to sandbox third-party embeds.

Three raw WebSocket endpoints are attached directly to the underlying http.Server (outside Express, since ws upgrades bypass Express middleware entirely and each one re-implements its own checks):

PathCarriesFile
/api/workspaces/:id/browser/streamLive browser video frames out, mouse/keyboard events inbrowser-ws.ts
/api/workspaces/:id/terminals/:sid/streamPTY bytes out, keystrokes/resize interminal-ws.ts
/api/stt/streamMicrophone audio in → local Whisper transcription outstt-ws.ts

Regular chat/agent token streaming does not use WebSockets at all — it rides a single unified Server-Sent-Events endpoint, GET /api/stream?scope=session|run|chat|global|automation&id=..., with Last-Event-ID resume support. That's the one durable "everything happening in the app" firehose; the three WebSockets above exist only because SSE is one-directional and these three features need to send bytes back up to the server.

3Core domain: ports, services, and the multi-harness router

packages/core follows a hexagonal (ports & adapters) shape: ports are interfaces describing what the domain needs (IAgentHarness, IBrowserBridge, ITerminalHost, a dozen repository interfaces); services implement the actual business logic against those interfaces; infrastructure holds the concrete adapters (Playwright, node-pty, the Electron CDP bridge). Swap an adapter and nothing in the service layer needs to change.

The most important abstraction is IAgentHarness — five composed capability interfaces (client lifecycle, model discovery, conversation lifecycle, messaging, events) that both the Copilot adapter and the Claude Agent adapter implement identically from the outside. A MultiHarness router pins each conversation to whichever provider created it, so one chat can run on Claude while another runs on Copilot in the same running server. This interface is one of the few things frozen as a stable, semver-protected SDK contract (per packages/sdk/API-STABILITY.md) — specifically so a third party can write their own harness adapter (e.g. for OpenAI) without waiting on GeneratorAI.

4Data layer

SQLite via Drizzle ORM, one file (default generatorai.db). Roughly 30 tables cover chats, workflow definitions/runs/stages, automations, projects, checkpoints, review threads, plan documents, and widget instances. A config seam (createDB(GENERATORAI_DATABASE_URL)) recognizes postgres:// / libsql:// URLs but deliberately throws "not yet wired" — SQLite is the only real driver today, by design (it's meant to be download-and-run, not a managed database).

Notable absence

There is no users table and no API-keys/credentials table anywhere in the schema. That's not an oversight — it's the direct consequence of the single-tenant design in §0, and it's the reason the entire auth story in §6 is one shared secret rather than accounts.

5Web, CLI, Desktop, SDK — four faces of one engine

  • Web (apps/web) — Vite/React SPA. Talks REST + SSE to /api, plus two raw WebSockets for the browser/terminal panels. Reads its API key out of localStorage and attaches it as Authorization: Bearer (or ?apiKey= for EventSource, which can't send custom headers).
  • CLI (apps/cli) — Ink/React terminal UI. Two modes: default HTTP mode talks to a running server exactly like the web app; a --local flag boots the SDK in-process instead (no server at all) via a DirectPlatformClient — useful for scripting/CI where spinning up a server is overkill. Anything server-only (webhooks, some project management) throws a clear "not available in --local" error rather than pretending to work.
  • Desktop (apps/desktop) — an Electron shell that does not reimplement the UI. It spawns the real server as a child process on a free loopback port, then simply loads that server's URL in a BrowserWindow. Same origin, same code, zero divergence from the web app — every new server feature "just works" on desktop for free.
  • SDK (packages/sdk) — createGeneratorAI({ provider, database }) gives you the whole engine as a library: facades for workflows, chat, automations, hooks, HITL, etc. A published API-STABILITY.md draws a hard line between the stable public surface and an /internal subpath (raw services, DAG internals) that can change without notice.

6Deep dive — authentication & credential management, end to end

This is the part most people expect to look like a normal SaaS app (login page, JWT, per-user accounts). It doesn't. Here is exactly what exists instead, and where the real gaps are.

6.1 · The trust model: one shared key, not user accounts

Think of GeneratorAI less like a website you log into, and more like a personal server you SSH into — the whole server has one front door, not per-user doors. There's no signup, no password, no session cookie, no "who am I" concept anywhere in the code.

flowchart LR
  C["Any client
(web tab, CLI, curl)"] -- "Authorization: Bearer <key>
or ?apiKey=" --> M["auth middleware
middleware/auth.ts"]
  M --> D{"GENERATORAI_API_KEY
env var set?"}
  D -- "no" --> OPEN["log ONE warning,
then let EVERY request through"]
  D -- "yes" --> CMP["compare with
crypto.timingSafeEqual"]
  CMP -- match --> OK["request proceeds"]
  CMP -- "no match" --> REJ["401"]

In code, that gate is one line in apps/server/src/app.ts:

app.use('/api', createAuthMiddleware({ apiKey: process.env['GENERATORAI_API_KEY'], logger }));

and the operator-facing warning that fires when nobody sets that env var, in middleware/auth.ts:

"[Auth] GENERATORAI_API_KEY not set — all /api routes are
 unauthenticated. This is UNSAFE for any deployment beyond localhost."

So: set GENERATORAI_API_KEY and the server checks one static bearer token on every /api request (timing-safe comparison, so an attacker can't guess it one character at a time by measuring response speed). Don't set it, and the server runs wide open — every route answers any request. /health and the raw webhook receiver are always exempt (webhooks verify themselves with an HMAC signature instead).

Worth knowing

app.listen(config.port, ...) in apps/server/src/index.ts passes no host argument, which means Node binds to every network interface, not just localhost. Combine that with the previous point: if you run this on a machine with a real network interface (a VPS, a LAN box) and never set GENERATORAI_API_KEY, the API is reachable — unauthenticated — from anywhere that can route to that machine. Only the separate widget-asset port explicitly binds to 127.0.0.1. The desktop app never sets this key either; it relies entirely on nobody else being able to reach the loopback port its embedded server happens to pick.

6.2 · How the AI providers (Copilot / Claude) actually get their credentials

GeneratorAI itself does not ask you for an OpenAI-style API key on first run. Instead it spawns the vendor's own official CLI as a subprocess and lets that CLI handle login — GeneratorAI just inherits whatever credential is already sitting in the environment or in that CLI's own credential store.

In other words: rotating a key means re-running that vendor's login command or restarting the server with a new env var — there is no in-app "update your API key" flow for the base harness credential. A third harness type, anthropic (meant for calling the raw Anthropic API directly, no CLI), is read from config but not actually wired into the provider factory yet — passing it currently throws "Unknown harness type", so treat it as unfinished, not usable.

6.3 · The one place a user-entered key does exist: BYOK per chat/workflow

There is a real "bring your own key" path — but it's scoped to a single chat or workflow stage wanting an OpenAI-compatible custom endpoint, not the base harness login above. A chat/workflow request body can carry a provider: { baseUrl, apiKey, model } object, which flows straight into the SDK's session config.

No encryption anywhere

That BYOK apiKey, once saved, is stored as plaintext JSON inside a SQLite text column (harnessConfig / harnessConfigOverrides in packages/db/src/schema.ts). Same story for the GitHub PAT in §6.4. There's no keychain integration, no column-level encryption, no envelope encryption anywhere in this codebase — keytar/Electron's safeStorage API are mentioned only in a future-features planning doc, never actually imported. The one real safety net is log redaction: the Pino logger config masks fields named apiKey, secret, token, password, and common auth headers before anything hits stdout — so secrets won't leak into logs, but they sit in plaintext at rest.

6.4 · Source-control (GitHub) credentials — the template for "settings-page secrets"

This is the closest thing to a real credentials UI in the app, and it's the pattern worth understanding since it's reused conceptually elsewhere: Settings → a plain text <Input> for a GitHub Personal Access Token → PUT /api/source-control/config → written to a plaintext JSON file on disk (source-control.json in the data directory) by SourceControlConfigService. The API response deliberately never echoes the raw token back (it returns { configured: true } instead), but the file on disk is unencrypted — anyone with filesystem access to that machine's data directory can read it directly. If no token is configured, it falls back to whatever the gh CLI already has stored from its own login.

6.5 · Desktop ↔ server internal handshake (a different, better-designed mechanism)

Ironically, the one place in this codebase with genuinely careful auth is an internal, invisible-to-the-user channel: how the Electron main process proves to its own embedded server that it's really the trusted desktop shell, not a stray web page.

1Electron main generates a random token once per app launch and puts it in the child server process's environment as GENERATORAI_ELECTRON_IPC_TOKEN — never sent over any network, just inherited process memory.
2Every request to POST /internal/browser/cdp-endpoint must satisfy two independent checks: the TCP connection's remote address must literally be 127.0.0.1/::1 (server-side loopback check, can't be spoofed by anything not already running on that machine), and the request must carry Authorization: Bearer <that token>, compared with the same timing-safe method as the API key.
3That token only authenticates the handshake — "yes, register this CDP endpoint" — not the CDP traffic itself. Each individual browser-tab proxy gets its own separate random token embedded directly in its WebSocket URL (more in §7).

6.6 · Gaps worth flagging

Finding

browser-ws.ts — the WebSocket that streams live browser video and accepts mouse/keyboard input — has no authentication and no Origin check at all. Its sibling endpoints (terminal-ws.ts, stt-ws.ts) both explicitly re-implement the same bearer-token + origin-allowlist check the REST API uses; browser-ws.ts skips both, with no comment explaining why. Anything that can reach the HTTP port and knows a workspace ID can watch the live browser feed and inject input. This looks like an accidental gap rather than a deliberate decision, and is arguably the most sensitive of the three WebSocket endpoints to leave open.

Finding

An HTTP-type MCP server configuration (HarnessConfig.mcpServers) has no dedicated field for an API key or auth header — only url/command/args. A key would have to be smuggled into the URL's query string, which also means it wouldn't get caught by the log-redaction rules described in §6.3 (those only match field names like apiKey, not substrings inside a url field).

7Deep dive — the browser relay / CDP bridge

This is the newest, actively-in-progress piece of the codebase (uncommitted on dev as of this review). It's the mechanism that lets an AI agent literally drive a browser — click things, read the page, take screenshots — and it's also the feature your "relay" and "mobile" questions are really about, so it gets a full walkthrough plus an honest answer on mobile.

7.1 · The problem it's solving

An agent that wants to "use a browser" has two very different ways to do it, and GeneratorAI supports both behind one common interface (IBrowserBridge):

  • A hidden browser the agent owns (the web-app / non-desktop path) — a real Chromium instance launched on the server that nobody else is looking at, with its picture streamed to the UI so a human can watch. Implementation: ServerPlaywrightHost.
  • The exact tab the human is already looking at (the desktop-app path) — instead of a second hidden browser, the agent reaches into Electron's own on-screen browser view and drives that, so the human sees every click happen live on their own screen, no second window, no video stream needed. Implementation: ElectronBridgeAdapter.

The second mode is the interesting engineering problem, because Electron's browser views don't normally expose a remote-debugging port at all — and the old--remote-debugging-port flag for the whole app was a real security hole: that one flag exposes every window in the app over one unauthenticated local port, including the app's own privileged main window (which has Node.js access via the preload script). Any web page a user visits inside that debuggable browser could, in theory, discover that port and reach into the privileged window through it.

Why the CI guard exists

scripts/check-no-app-wide-cdp.mjs is a build-time grep that fails the pipeline if the dangerous flag (appendSwitch('remote-debugging-port', ...)) ever reappears anywhere under apps/desktop. It's a tripwire against that old, unsafe design regressing.

The fix is a component called ScopedCdpProxy (apps/desktop/src/main/cdp/): instead of one global debugging port for the whole app, it opens a debugging channel for exactly one browser tab at a time — the one currently active — on its own random local port, guarded by its own random token baked into the WebSocket URL. It talks to that single tab using Electron's built-in webContents.debugger API (a programmatic CDP interface, not a network port at all) and re-exposes it as a normal CDP WebSocket server just so that standard tools like Playwright, which only know how to speak CDP-over-WebSocket, can attach to it.

7.3 · How "multiple clients" actually works

This is the real mechanic behind your "relay" question, and it only applies to the screencast (web/server) path — the native desktop path doesn't need it, since there's only ever one physical screen to look at.

Inside ServerPlaywrightHost, the screencast is a shared, ref-counted subscription: the first viewer to connect triggers Page.startScreencast on the one real Chromium instance; every viewer after that just gets added to a subscriber set and rides the same frame stream — nobody starts a second screencast. The underlying capture only stops once the last subscriber disconnects. So if the same chat is open in two browser tabs, both get the identical live video feed for free, fanned out from one source — that's the "relay" behavior: one real browser, many simultaneous viewers.

But no control arbitration

Input is not similarly coordinated. Whichever client sends a click/keystroke message gets it applied immediately — there's no "who's in control" concept, no locking, no last-writer-wins protection beyond each individual connection's own local ordering. Two people (or two tabs) sending input to the same workspace at once would genuinely race.

7.4 · The honest answer on "mobile connection"

Direct answer

There is no phone-pairing, QR-code, or "companion app" feature anywhere in this codebase. I searched specifically for mobile/remote/pairing/QR/device/companion patterns across the relay and desktop code and found nothing resembling that. The only place the word "mobile" appears is as a Chrome DevTools device-emulation parameter (BrowserEmulationParams.mobile) — that's the desktop app telling its own on-screen browser tab "render as if you were a mobile viewport," the same toggle you'd click in Chrome's DevTools device toolbar. It has nothing to do with connecting from an actual phone.

What genuinely does exist, and is probably what prompted the question, is the multi-client fan-out from §7.3: several browser tabs of the same web app can watch and drive the same live browser session simultaneously. If you opened the web app's URL on your phone's browser and that phone could reach the server over the network, it would technically work the same way a second desktop tab does — the app has no device-type check. But that's an incidental side-effect of the server binding to all interfaces (§6.1's gap), not a designed or supported mobile flow: there's no responsive mobile layout tuning, no session hand-off UX, and — per §6.6 — that WebSocket has no auth check, so this "works by accident" path is not one to rely on for anything beyond a local trusted network.

8Summary

Architecture: one server, one core engine, four faces (web/desktop/CLI/SDK), multi-harness by design, SQLite-first and deliberately single-tenant.

Auth: a single shared bearer token gates the whole API (or nothing, if unset) — there are no user accounts. LLM credentials are delegated to the vendor CLIs' own login flows; the one place users type in a secret (GitHub PAT, BYOK keys) is stored as unencrypted plaintext, mitigated only by log redaction. The desktop↔server internal handshake is the one exception — genuinely double-guarded with loopback + token checks.

Relay: the "relay" is a screencast fan-out inside ServerPlaywrightHost — one real Chromium, many viewers, all riding the same frame stream — plus, on desktop, a scoped per-tab CDP proxy that lets the agent drive the exact browser view the human is already looking at. There is no mobile-pairing feature; "multiple clients" means multiple tabs of the same web app, not a phone.

Two concrete gaps worth acting on if this is heading toward anything beyond a single trusted machine: give browser-ws.ts the same auth/origin check its sibling WebSockets already have, and make the server bind to 127.0.0.1 by default unless an operator explicitly opts into a wider bind alongside setting GENERATORAI_API_KEY.
