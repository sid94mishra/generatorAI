Connections and security: every client, every network

How the desktop app, browsers, the mobile app, the CLI and agents connect to a GeneratorAI server, what is broken or unsafe today, how modern agent products solve the same problems, and the fixes that make every scenario secure and seamless.

01Verdict

The cryptographic core is strong: device keys that never leave the device, standards-correct DPoP-bound tokens, fail-closed startup, a name-constrained private CA, and solid Electron renderer hardening. The problems are at the edges.

  • One critical authorization bypass. Changing the case of a URL (/auth/Devices) skipped the permission check, so any paired device, even a read-only agent, could manage devices, read the audit log, mint an all-access pairing code and open terminals. Reproduced. Being fixed now.
  • Three more confirmed bugs.
    • Revoking a device doesn't cut its live streams.
    • Pairing can be locked out. One attacker on the Wi-Fi can block pairing for everyone.
    • An agent device can relabel itself to become eligible for terminal and admin rights.
    Being fixed now.
  • Remote access is not usable yet.
    • The relay is turned off for clients and isn't end-to-end encrypted.
    • The mobile app's home-network connection is unencrypted.
    • Browsers on another device face a certificate warning and a fingerprint comparison most people will skip.
    • The desktop app can't connect to another machine's server.
Recommended direction: pin the server's own certificate authority from the pairing QR on every native client. That one change secures the home network and the relay at the same time. Then make "connect anywhere" the default: relay first, home network when it's reachable. This is the pattern Plex, Home Assistant Cloud, JetBrains Code With Me and OpenAI Codex use. It needs no vendor certificate infrastructure.

03Bugs, being fixed now

All reproduced against isolated servers. An agent is fixing them now, each with a regression test that fails before the fix and passes after.

B-1 · F-1

Changing URL case skips the permission check

criticalfixing
Evidence

A read-only agent device got 403 on GET /api/auth/devices but 200 on /api/auth/Devices. It also:

  • read the full audit log via /Audit;
  • minted an all-access pairing grant via POST /Pair;
  • revoked another device;
  • reached terminal and computer-use routes.

The policy compares path segments case-sensitively (packages/auth/src/routePolicy.ts:276), while Express 5 routes case-insensitively by default. A mismatched path falls to a shorter, weaker rule instead of failing closed.

Why it matters

Complete privilege escalation from any paired device. This is OWASP's number-one class, Broken Access Control. DPoP doesn't help, because the attacker signs the URL they are attacking (RFC 9449 works as designed).

Fix

Normalise the path once, for both REST and WebSocket upgrades, and compare canonically. Any path that doesn't match its real rule fails closed to the admin default. A test checks every policy entry under mixed case, trailing and double slashes.

Why this fix

Patching only the router (case-sensitive routing) would leave the policy logic fragile. Normalising at the policy and failing closed fixes the class of bug, not just this instance.

B-2 · F-2

A revoked device keeps receiving live events

highfixing
Evidence

After revoke, the device's already-open stream received chat.created and chat.updated for 35 s and more. Revocation is checked only on the next request or ticket; nothing closes live connections.

Why it matters

Revoke exists for lost phones and compromised laptops. "Cut off now" must mean now. The audit log records revocation as critical, implying an immediacy the data path didn't honour.

Fix

Index live SSE, WebSocket and relay streams by device, and close them on revoke, credential rotation and loss of stream scope.

Why this fix

Re-checking on each heartbeat would still leave a window and add load. Closing on the event is immediate and costs nothing at rest. Claude's Trusted Devices and Codex host lists both treat revoke as immediate.

B-3 · F-3

One attacker on the Wi-Fi can lock out pairing

highfixing
Evidence

70 bogus previews from one address filled the single global limit (60/min). A genuine code from another address then got 429.

Why it matters

Pairing is how you recover access with a replacement device. Its availability was controlled by any unauthenticated peer on the network.

Fix

Make the per-address limit the primary one, so no single address can spend the global budget. Owner-initiated pairing is exempt. The UI gets a clear message ("too many attempts from this network, try again in N s").

Why this fix

It keeps brute-force protection (per-address and per-code limits stay) while removing the denial-of-service lever.

B-4 · F-5

An agent device can relabel itself to gain terminal and admin rights

mediumfixing
Evidence

A grant minted for an MCP agent was completed with platform: "cli". The device was then granted exec:terminal and admin:settings successfully (DeviceService.ts:485 lets the body's platform win).

Why it matters

It breaks the rule that agents never hold terminal or admin rights. It can also make an agent count as a person for approval decisions.

Fix

Pin the platform at grant time, never allow an agent to become something else, check every later scope change against the grant, and log mismatches.

Why this fix

The grant is minted by the owner, so it is the trustworthy source. The joining client is not.

B-5

Host-header check against DNS rebinding

verifyfixing if missing
Evidence

The research found DNS rebinding is the recurring way local AI servers get attacked from a web page (Ollama CVE-2024-28224). The audit's list of solid parts doesn't include a Host allow-list.

Why it matters

Without it, a malicious website can point its own domain at 127.0.0.1 and talk to the local server as a "same-origin" page. Public routes like pairing preview are exposed first.

Fix

Accept only known names: loopback, the advertised network addresses and .local name, a custom certificate's names, and trusted-proxy hosts. Anything else gets a clear rejection, before authentication, on REST and WebSocket alike.

Why this fix

It is the standard mitigation (NCC's Ollama advisory, MCP security guidance). Origin checks alone don't stop rebinding, because the rebound page is same-origin.

B-6 · F-6, F-9, F-7

Smaller hardening

medium–lowfixing
Evidence
  • Pre-pairing exposure: the public server info gives anyone on the network the machine's real hostname and every interface. Low-privilege devices can read the secret-store backend and bind address.
  • Misleading CORS errors: a blocked origin returns 502 UNKNOWN_ERROR with a stack trace in dev.
  • DPoP URL canonicalisation: it doesn't lower-case the host.
Fix

Show the display name instead of the hostname, and only the addresses pairing needs. Move security-posture details behind admin. Return 403 ORIGIN_NOT_ALLOWED and never put stacks in responses. Normalise the host in DPoP.

04Design gaps that need your decision

G-1

Mobile app uses plain HTTP on the home network

highdecide
Evidence

D-112 deliberately kept a plain-HTTP lane for the native app (MV-44). Signatures stop token replay, but anyone on the Wi-Fi can read chats, code and diffs, and can intercept first pairing.

Why it matters

Hotel, office and café networks are shared. Nothing tells the user this hop is unencrypted.

Fix

Carry the server's CA fingerprint in the pairing QR (it already does). Then add small native trust modules that accept exactly that CA, loaded at runtime, then delete the plain-HTTP lane:

  • an iOS URLSession delegate using SecTrustSetAnchorCertificates;
  • an Android OkHttp HandshakeCertificates.

They cover fetch, streaming and WebSocket. The QR also includes a backup key hash, so a future CA rotation doesn't force re-pairing.

Why this fix

The off-the-shelf React Native pinning libraries (TrustKit, react-native-ssl-public-key-pinning) pin on top of system trust, so they still reject a private CA. Build-time pins (NSPinnedDomains, Android <pin-set>) can't express a CA that is different for every install.

Runtime anchors are the only correct mechanism, and they are what Code With Me does by putting the host fingerprint in the join link. This is also the foundation for G-2.

G-2

Remote access: the relay is off for clients and not end-to-end encrypted

highdecide
Evidence

Asking for relay access returns 409 RELAY_CLIENT_UNAVAILABLE, so phones and other machines can't reach the server from outside the home network today. The relay forwards raw bytes but can read them; the docs say so honestly.

Why it matters

"Use my agent from my phone anywhere" is the headline feature of 2026 agent apps: Claude Code Remote Control, Codex remote, Warp, Cursor. Most of them route through a relay that can read everything. Codex is the exception, with Noise-encrypted relay channels and one-to-one QR pairing per phone and host.

Fix

Run the client's TLS session, pinned to the install's CA as in G-1, end to end through the existing relay. The host bridge targets the TLS listener, and the relay sees only timing and volume. Then enable the relay client transport.

Why this fix

Plex Relay, Home Assistant's SniTun and JetBrains Code With Me all carry the endpoint's own TLS through a blind relay rather than inventing new crypto. We get one crypto stack, already pinned by G-1, and the existing NaCl framing (e2ee.ts) stays as a fallback. A Codex-style Noise channel is equally secure but adds a second protocol to maintain.

G-3

Browsers on another device: warning plus a fingerprint check

mediumdecide
Evidence

Today a user clicks through "Your connection is not private" and is meant to compare a SHA-256 prefix. That comparison is the only protection on first connect, and it is exactly the step people skip. The browser also shows "Not secure", and it can't install as an app.

Why it matters

No public certificate authority will issue for a private IP or a .local name (CA/Browser Forum rules; Let's Encrypt's IP certificates need a public address). Without help, a browser on the LAN always sees a warning.

Fix, now

Guide a one-time CA install first. The pairing screen gets a QR to the CA download, with step-by-step instructions per OS (including the iOS "full trust" toggle). After that, no warnings or fingerprint check ever. Promote the Tailscale route (tailscale cert or Serve), which already works with a trusted certificate.

Option, later

Per-install public certificates, the plex.direct / *.ts.net pattern: a vendor domain whose names resolve to the LAN IP, plus a wildcard certificate per install via DNS-01. This gives zero-warning browsers anywhere and true end-to-end browser sessions through the relay. It costs vendor DNS and certificate infrastructure, Let's Encrypt rate limits, names in public certificate logs, and some routers block it. It's worth it only if browser access from anywhere is a priority.

Why

The guided CA install removes the risky manual step with no infrastructure. The public-certificate route is the only way to zero warnings, and it is a strategic decision.

G-4

The desktop app can't connect to another machine's server

mediumdecide
Evidence

Remote mode only trusts certificates on localhost (certificate-error handler), so another GeneratorAI's built-in HTTPS fails with a dead page.

Fix

Pair the desktop app like any client, by QR or code with the fingerprint. Then accept exactly that server's CA via session.setCertificateVerifyProc, returning accept only on an exact CA key match and Chromium's own verdict otherwise. Show a clear "trust this server?" step with the fingerprint.

Why this fix

Electron's documented safe pattern. Accepting per hostname would let anyone on that address impersonate the server.

G-5 · F-4

Desktop app hardening fuses are off

mediumbefore release
Evidence

The packaged app ships these settings:

  • RunAsNode, NODE_OPTIONS and --inspect: enabled;
  • ASAR integrity: off;
  • signing: ad-hoc.
Why it matters

Any process that can launch the app with an environment variable can run code inside it, and it holds the unlocked vault key. These are Electron's standard local-escalation and supply-chain protections.

Fix

Start the embedded server with utilityProcess.fork instead of ELECTRON_RUN_AS_NODE, so RunAsNode can be disabled. Disable the other two, enable ASAR integrity and app-only loading, and sign and notarize. Check the Windows and Linux builds too.

G-6

Connect anywhere: route choice and OS network permissions

UXdecide
Evidence

Every OS now gates local-network access:

  • iOS 14+: the Local Network prompt.
  • Android 17: ACCESS_LOCAL_NETWORK, required when targeting SDK 37.
  • Chrome 142+: Local Network Access, extended to WebSockets in 147.

Products that feel seamless (Claude Code, Codex, Tailscale, Plex) connect through the relay first and upgrade to a direct path when it's reachable.

Fix

After G-2, native clients start on the relay. They probe the LAN address with a pinned TLS handshake and switch when it answers. They handle "Local Network denied" with a clear "allow in Settings" message, and add the iOS usage string and the Android permission.

G-7

Device lifecycle and recovery

UXdecide
Fix

Add the controls modern products have:

  • idle expiry and a "last seen" for each device;
  • "sign out everywhere";
  • a notice on every device when a new one pairs;
  • approvals that time out and fail closed (Dispatch auto-denies after 10 min);
  • a recency-based Face ID step-up for risky approvals;
  • a documented in-app path for "I lost all my devices". It exists today only as a file or CLI step.

If pairing by typed code without the QR stays, move it to a password-authenticated exchange (CPace), so an interceptor gets one guess instead of an offline brute force.

G-8

Smaller known gaps

low
Items
  • Widgets: they load only on the host machine. Serve their isolated origin through the same TLS listener on its own port.
  • Vault key handoff: it goes to the server through an environment variable, which a same-user process can read. Hand it over through a pipe instead (optional under the single-user model).

05What is solid — keep it

  • DPoP implementation: strict algorithms, replay and nonce handling, thumbprint binding, matching RFC 9449.
  • Token model:
    • short access tokens bound to the device key;
    • hashed rotating resume credentials;
    • single-use stream tickets;
    • signed links that can't carry exec or admin rights;
    • scope cuts take effect live on REST.
  • Fail-closed startup: no vault key, no production server, and no unauthenticated mode off loopback.
  • LAN transport:
    • plain-HTTP pages redirect to HTTPS, and plain-HTTP API calls from browsers are refused;
    • the CA is name-constrained to private addresses and .local, so trusting it can't vouch for any public site;
    • custom certificates are validated;
    • forwarded headers are trusted only from named proxies.
  • Electron renderer hardening: isolation, sandbox, navigation and IPC guards, the scoped CDP proxy and widget origin isolation.
  • Pairing grants: single-use, 10 minutes, 5 attempts, proof of key on completion. Preview gives away nothing.
